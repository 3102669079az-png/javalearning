# 一、Java 语言核心

## 1.1 类与对象

**一句话**：类是一张图纸，对象是按图纸造出来的房子。

```java
public class Book {
    private String name;      // 字段：每个对象各有一份
    private int price;

    public Book(String name, int price) {   // 构造器：造对象时自动执行
        this.name = name;
        this.price = price;
    }

    public void print() {      // 方法：对象能做什么
        System.out.println(name + ", " + price + "元");
    }
}
```

### 必须记住的四件事

**① 字段用 `private`，通过方法访问（封装）**

不是"习惯问题"，是**不变量保护**。字段公开，外面就能随便改，你的校验形同虚设。

**② 构造器的名字必须和类名一样，没有返回类型**

写 `public void Book(...)` 不是构造器，是一个普通方法 —— **编译通过，但 `new Book()` 永远调不到它。**

**③ `this` 指的是"当前这个对象"**

只有参数名和字段名冲突时才必须写 `this.name = name`。不冲突时可以不写。

**④ 类名首字母大写**

`Book` 不是 `book`。Java 的命名约定，不是语法强制，但**全行业都这么写，不这么写会被认为不专业**。

### 不变量与 setter

> **不变量（invariant）= 这个对象在任何时刻都必须成立的条件。**

| 类 | 不变量 | setter 策略 |
|---|---|---|
| `Circle` | `r > 0`（单字段） | 可以有 `setR()`，里面做校验 |
| `Triangle` | `a + b > c`（**多字段联动**） | **不能**有独立的 `setA()`，因为单改一个会破坏不变量 |

**多字段共享一个不变量时，只能整体替换，不能单独改一个。**

## 1.2 继承与多态

```java
public class EBook extends Book {
    private int fileSize;

    public EBook(String name, int price, int fileSize) {
        super(name, price);      // ← 必须是构造器第一行
        this.fileSize = fileSize;
    }

    @Override
    public void print() {        // 重写父类方法
        super.print();
        System.out.println(fileSize + "MB");
    }
}
```

### 多态：Java 最核心的一件事

```java
Book b = new EBook("三体", 23, 5);
b.print();     // 调用的是 EBook 的 print()，不是 Book 的
```

**编译时看左边，运行时看右边。**

- 左边的 `Book` 决定**能调用哪些方法**（编译期检查）
- 右边的 `EBook` 决定**实际执行哪个版本**（运行期动态绑定）

这就是为什么 `ArrayList<Book>` 里能混装 `PaperBook` 和 `EBook`，一个循环全部正确打印。

### 什么时候必须用父类引用

不是所有地方都要。三种典型场景：

1. **集合统一管理**：`List<Book> shelf` 装各种子类
2. **方法参数通用化**：`void printAll(List<Book> books)`
3. **面向接口编程**：`Downloadable d = new EBook(...)`

### 重载 vs 重写

| | 重载 Overload | 重写 Override |
|---|---|---|
| 发生在 | **同一个类**里 | 父子类之间 |
| 方法名 | 相同 | 相同 |
| 参数列表 | **必须不同** | **必须相同** |
| 返回类型 | 无所谓 | 相同或是子类型 |
| 作用 | 同一个动作的不同入参形式 | 子类改变父类的行为 |

```java
void print()          {}
void print(String s)  {}   // 重载：参数不同

@Override
void print()          {}   // 重写：一模一样
```

### 重写的三级限制

1. **访问权限不能变小**：父类 `public`，子类不能写成 `protected`
2. **不能抛更宽的受检异常**
3. **`static` 方法不能被重写**（它属于类，不属于对象）

## 1.3 抽象类 vs 接口

| | 抽象类 `abstract class` | 接口 `interface` |
|---|---|---|
| 关键字 | `extends`（单继承） | `implements`（可多实现） |
| 能有构造器吗 | **能**（但不能直接 `new`） | 不能 |
| 能有字段吗 | 能，任意类型 | 只能是 `public static final` 常量 |
| 能有方法体吗 | 能，普通方法 | Java 8 起可以用 `default` |
| 表达什么 | **"是什么"**（is-a） | **"能做什么"**（can-do） |
| 什么时候用 | 有共享的字段和实现 | 只需要约定一组能力 |

```java
public abstract class Book {          // 抽象类：书都有名字和价格
    protected String name;
    public abstract String getType(); // 抽象方法：子类必须实现
}

public interface Downloadable {       // 接口：能下载
    void download();                  // 默认就是 public abstract
}
```

### 三个必踩的坑

**① 抽象类不能实例化**

```
java: Book is abstract; cannot be instantiated
```

正确理解：不是"不能用"，是"**没资格直接用**"。它的子类可以。

**② 接口方法默认 `public`，实现时必须写 `public`**

```java
@Override
void download() { }          // ✗ 编译错误：正在尝试分配更低的访问权限

@Override
public void download() { }   // ✓
```

**③ 漏写 `implements` 时，`@Override` 会报错**

```
java: 方法未从其超类重写方法
```

因为编译器找不到父类上有这个方法。**看到这个错误，先检查 `implements` 写了没。**

## 1.4 异常

```
Throwable
├── Error                  ← 程序无法处理（OutOfMemoryError）
└── Exception
    ├── 受检异常 Checked    ← 编译器强制你处理（IOException）
    └── RuntimeException    ← 非受检，运行时才炸（NullPointerException）
```

### 核心区别

| | 受检异常 | 运行时异常 |
|---|---|---|
| 必须 `try-catch` 或 `throws` 吗 | **必须** | 不强制 |
| 代表什么 | 外部环境问题（文件不存在、网络断） | 代码 bug（空指针、数组越界） |
| 例子 | `IOException`、`SQLException` | `NullPointerException`、`NumberFormatException` |

### 自定义业务异常

```java
public class BookException extends RuntimeException {
    public BookException(String message) {
        super(message);
    }
}
```

**为什么继承 `RuntimeException` 而不是 `Exception`？**

因为业务校验失败（价格不能为负）属于**调用方用错了**，不是环境问题。继承 `RuntimeException` 就不用每次都在方法签名上写 `throws`，调用方的负担小。

### try-catch-finally 的执行顺序

```java
try {
    return 1;
} finally {
    System.out.println("一定会执行");
}
```

`finally` **一定会执行**，即使 `try` 里有 `return`。执行顺序是：算好返回值 → 执行 `finally` → 真正返回。

> **注意 `finally` 里有 `return` 会覆盖 `try` 的返回值** —— 这是经典面试坑，也是实际项目里绝对不该写的代码。

### 三个容易混的词

- `final` —— 修饰符，表示"不能改"（变量、方法、类）
- `finally` —— 代码块，表示"一定执行"
- `finalize()` —— 方法，GC 前调用（**已废弃，不要用**）

## 1.5 集合

### ArrayList

```java
ArrayList<Book> shelf = new ArrayList<>();
shelf.add(new Book("活着", 45));
shelf.get(0);
shelf.remove(0);        // 按下标删
shelf.size();
for (Book b : shelf) { } // 增强 for
```

**底层是数组。** 默认容量 10，满了扩容到 **1.5 倍**。

**优点**：随机访问 O(1)（`get(i)` 直接算地址）
**缺点**：中间插入/删除 O(n)（要把后面所有元素往前挪）

### 经典坑：`remove(int)` vs `remove(Object)`

```java
ArrayList<Integer> list = new ArrayList<>(List.of(1, 2, 3));
list.remove(1);              // 删除【下标 1】，即元素 2
list.remove(Integer.valueOf(1));  // 删除【元素 1】
```

**为什么？** 因为 `remove(int index)` 和 `remove(Object o)` 是重载。传 `int` 走下标版本，传对象走元素版本。

### HashMap

```java
HashMap<String, Book> shelf = new HashMap<>();
shelf.put("活着", new Book(...));
shelf.get("活着");            // O(1)
shelf.containsKey("活着");
shelf.remove("活着");         // 只能按 key 删
for (String key : shelf.keySet()) { }
```

**底层（JDK 8）**：数组 + 链表 + 红黑树

```
hash(key) → (n-1) & hash → 数组下标
                            ↓
                     同一格子里的元素用链表串起来
                            ↓
                     链表长度 ≥ 8 且数组长度 ≥ 64 时，转红黑树
```

**四个关键数字**：

| 参数 | 值 | 含义 |
|---|---|---|
| 默认容量 | 16 | 数组长度，**永远是 2 的幂** |
| 负载因子 | 0.75 | 元素数 / 容量超过它就扩容 |
| 扩容 | 2 倍 | 容量翻倍，所有元素重新分布 |
| 树化阈值 | 8 | 链表长度达到 8 转红黑树 |

**为什么容量必须是 2 的幂？**

因为 `(n-1) & hash` 只有在 n 是 2 的幂时，才等价于 `hash % n`，而且位运算比取模快得多。

**为什么要 `h ^ (h >>> 16)`？**

让高位也参与运算。否则 `hash` 的高 16 位在 `& (n-1)` 时全被丢掉，低位相同的 key 会挤在一起。

### equals 与 hashCode 的契约

> **重写 `equals` 必须同时重写 `hashCode`。**

- 两个对象 `equals` 相等 → `hashCode` **必须**相等
- `hashCode` 相等 → `equals` **不一定**相等（哈希冲突）

**反例（只写 equals 不写 hashCode）**：两个 `equals` 相等的对象哈希值不同 → 被放进不同的格子 → `HashMap.get()` 找不到它。

**反例（只写 hashCode 不写 equals）**：哈希值相同但 `equals` 是引用比较 → 同一个格子里判定为不同对象 → 也找不到。

### `==` vs `equals`

```java
String a = new String("abc");
String b = new String("abc");
a == b        // false（比较引用地址）
a.equals(b)   // true（比较内容）

Integer x = 127, y = 127;
x == y        // true（Integer 缓存 -128~127）
Integer m = 128, n = 128;
m == n        // false（超出缓存，是两个对象）
```

**结论：比较内容永远用 `equals`，`==` 只用于基本类型和判 null。**

## 1.6 文件 IO

```java
// 读
List<String> lines = Files.readAllLines(Path.of("shelf.txt"));

// 写
Files.write(Path.of("shelf.txt"), lines);
```

比老的 `FileReader`/`BufferedReader` 简洁得多。**新的项目优先用 `java.nio.file`。**

### try-with-resources

```java
try (BufferedReader br = Files.newBufferedReader(path)) {
    ...
}   // 自动 close，即使抛异常
```

括号里声明的资源，离开 `try` 块时会**自动关闭**，关闭顺序与声明顺序**相反**。

**为什么重要**：不关闭 → 文件句柄泄漏 → 最终 `Too many open files`。

## 1.7 泛型

### 为什么需要泛型

```java
// 没有泛型：什么都能装
public class ObjectBox {
    private Object content;
    public void set(Object c) { content = c; }
    public Object get()      { return content; }
}

ObjectBox box = new ObjectBox();
box.set("三体");                 // 编译器一句话都没说
Book b = (Book) box.get();       // 运行到这里才炸
// Exception in thread "main" java.lang.ClassCastException:
//   class java.lang.String cannot be cast to class Book
```

**问题不在于强转，在于编译器全程没拦。**

### 正确使用泛型形参

```java
public class Box<T> {
    private T content;                 // ← T 必须出现在字段上
    public void set(T c) { content = c; }
    public T get()       { return content; }
}

Box<Book> box = new Box<>();
box.set("三体");
// 编译错误：不兼容的类型: java.lang.String无法转换为Book
```

### 泛型形参没被使用（踩过的坑）

```java
public class Box<T> {                 // 声明了 <T> …
    private Object content;           // … 但字段是 Object
    public void set(Object c) { content = c; }
    public Object get()       { return content; }   // T 一次都没出现
}
```

报错：`不兼容的类型: java.lang.Object无法转换为Book`

> **判据：塞一个 `String` 进去。编译报错 = 泛型形参真的生效了；编译通过 = 形参是摆设。**
> **关键不在类名后面那个 `<T>`，在 `T` 有没有真的出现在字段、参数、返回值上。**

### ⚠️ 术语纠错（2026-11-20 修正）

上面这个"形参是摆设"的写法，**不要叫它"假泛型"**。我一开始就是这么叫的，被 AI 校对指出来，它是对的。

在 Java 圈里，「真泛型 / 伪泛型」这组词**指的是 Java 和 C# 的对比**，不是"有没有真的用 T"：

| | 机制 | 俗称 |
|---|---|---|
| **Java 泛型** | 类型擦除：编译后 `T` 变成 `Object` 或上界 | 常被叫「伪泛型」 |
| **C# 泛型** | CLR 在运行时保留类型参数 | 「真泛型」 |

**所以"Java 的泛型是伪泛型"这句话是对的**（相对 C# 而言）。而我当时说的"这个 Box 是假泛型"是用错了词——那个写法该叫：**泛型形参未被使用** / **空泛型壳子**。

**为什么这个区别重要——面试会扣分：**

- 问「Java 泛型和 C# 泛型有什么区别」→ 答「Java 用类型擦除，C# 运行时保留类型信息」✅
- 答「Java 是假泛型，因为我写了 `<T>` 没用它」❌ 完全跑偏

### 类型擦除

`javap -p -s Box.class`：

```
public void set(java.lang.Object);
    descriptor: (Ljava/lang/Object;)V
public java.lang.Object get();
    descriptor: ()Ljava/lang/Object;
```

**上面两种写法（用了 `T` 的 / 没用 `T` 的）字节码完全相同。**

> **用了 T：编译器里有一切，字节码里什么都没有。**
> **没用 T：编译器里也没有，字节码里也没有。**

擦除之后，编译器会**在所有 `get()` 调用点自动插强转** —— 这就是为什么 `Box<Book>.get()` 能直接赋给 `Book`。

```java
Box<Book> a = new Box<>();
Box<String> b = new Box<>();
a.getClass() == b.getClass();     // true，运行期只有一个 Box 类
```

### 三条规则

1. `Box<Book>` 和 `Box<PaperBook>` **没有父子关系**（即使 `PaperBook extends Book`）
2. **不能 `new T()`**（擦除后不知道 T 是什么）
3. 不能 `instanceof T`、不能 `new T[]`

### 泛型方法

```java
public static <T> T lastOf(List<T> list) {
    return list.isEmpty() ? null : list.get(list.size() - 1);
}

Book last = lastOf(dao.findAll());     // 自动推断 T = Book
```

`<T>` 必须写在**返回值前面**，才算泛型方法（写在类名后是泛型类）。

### 菱形语法

`new ArrayList<Book>()` → `new ArrayList<>()`，右边的类型从左边推。

## 1.8 注解与反射

### 注解是标签

```java
@Retention(RetentionPolicy.RUNTIME)   // 保留到运行期，反射才读得到
@Target(ElementType.FIELD)            // 只能贴在字段上
public @interface AutoInject { }
```

### ⭐ 默认值陷阱（最容易静默失效的地方）

**`RetentionPolicy` 的默认值是 `CLASS`，不是 `RUNTIME`。**

忘了写 `@Retention(RUNTIME)` → 反射读不到 → **不报错、不警告、静默失效**。

IDEA 只在 `@interface` 定义那一行提示「注解 'AutoInject.class' 不保留用于反射访问」，**用注解的地方一个字都不会提示**。

| 策略 | 保留到 | 反射能读到吗 |
|---|---|---|
| `SOURCE` | 编译后丢弃（`@Override`） | 不能 |
| `CLASS` | class 文件里有，JVM 加载时丢弃（**默认**） | 不能 |
| `RUNTIME` | 运行期 | 能 |

### 反射读标签 + 干活

```java
public <T> T get(Class<T> clazz) throws Exception {
    Constructor<T> ctor = clazz.getDeclaredConstructor();
    ctor.setAccessible(true);
    T bean = ctor.newInstance();

    for (Field f : clazz.getDeclaredFields()) {
        if (f.isAnnotationPresent(AutoInject.class)) {
            Object dep = get(f.getType());       // ← 递归：依赖的依赖也会被装配
            f.setAccessible(true);               // ← 必须先开，否则 IllegalAccessException
            f.set(bean, dep);
            System.out.println("注入: " + clazz.getSimpleName() + "." + f.getName() + " <- " + dep.getClass().getSimpleName());
        }
    }
    return bean;
}
```

### private 能不能突破

**能。** `f.setAccessible(true)` 之后 `f.set(bean, dep)` 可以写私有字段。

反射破单例也一样：

```java
Constructor<HolderSingleton> c = HolderSingleton.class.getDeclaredConstructor();
c.setAccessible(true);
HolderSingleton evil = c.newInstance();
evil == HolderSingleton.getInstance()      // false —— 单例被破
```

枚举挡得住：`IllegalArgumentException: Cannot reflectively create enum objects`

### 三个角色

- **注解**是标签
- **反射**是读标签的手
- **容器**是那个真去干活的人

> 缺任何一个，`@Autowired` 就只是一个装饰。

### 递归陷阱

`get(f.getType())` 里又调了一次 `get()` —— **依赖的依赖也会被自动装配**。

好处是能自动串起来；坏处是 A 依赖 B、B 依赖 A 时会**无限递归直到栈溢出**。Spring 用三级缓存解决循环依赖。

## 1.9 多线程（一）：原子性

### 顺序完全不受你控制

两个线程各打印 A1..A12 / B1..B12，连跑 6 次输出全不同：

```
第 1 次：A1..A12  B1..B12
第 2 次：B1..B8  A1..A11  B9..B12  A12
第 3 次：B1..B5  A1  A2  B6  B7  B8  A3  B9..B12  A4..A12
```

> **线程的执行顺序由调度器决定，你的代码对顺序没有任何控制权。**

### `count++` 不是一步

它是**读 → 加 → 写**三步：

| 时刻 | 线程 A | 线程 B | count |
|---|---|---|---|
| 1 | 读 count → 0 | | 0 |
| 2 | | 读 count → 0 | 0 |
| 3 | 加 1 → 1 | | 0 |
| 4 | | 加 1 → 1 | 0 |
| 5 | 写回 1 | | **1** |
| 6 | | 写回 1 | **1** |

**两次加法，结果只加了 1。**

实测：两个线程各 `count++` 10 万次，连跑 5 次：

```
148512 / 121863 / 145384 / 144494 / 159034     期望 200000
```

**同一个程序、同一个输入，每次结果都不同，而且都是错的。**

### `synchronized`

```java
static int count = 0;
static synchronized void add() { count++; }
```

实测 3 次全部 200000。

### ⭐ 锁对象是谁（踩过的坑）

| 写法 | 锁的对象 | 作用范围 |
|---|---|---|
| `synchronized void add()` | `this` | **每个实例一把** |
| `static synchronized void add()` | `Xxx.class` | **整个 JVM 一把** |
| `synchronized(obj) { }` | obj | 按 obj 走 |

**坑**：数据是 `static int count`，方法却写成了 `synchronized void add()`（漏了 static）。两个线程各 `new` 一个对象 → 各拿各的锁 → 完全不起作用。

实测丢 **6367–13690**。**代码里明明写了 `synchronized`，结果还是错的。**

> **锁必须锁在"被保护的那份数据"上。数据是 static 的，锁就必须是 static 的。**

### 和 MySQL 行锁的对照

| | MySQL 行锁 | Java `synchronized` |
|---|---|---|
| 生效范围 | **跨连接**，多台机器都受约束 | **只在本 JVM 内** |
| 多台服务器部署 | 有效 | **完全无效** |

**所以：单机 `synchronized` 挡不住多服务器并发。** 那种场景要么靠数据库锁，要么靠 Redis 分布式锁。

### `start()` vs `run()`

`t.run()` 是普通方法调用，**在当前线程里执行**；`t.start()` 才真的启动新线程。

### `sleep(0)` 的错觉

去掉锁、在 `count++` 后面加 `Thread.sleep(0)`，丢失量从 3–6 万降到 **443**。

再跑 8 次：`510 / 1358 / 834 / 321 / 364 / 1619 / 493 / 762` —— **没有一次等于 0**。

> **时间窗口缩小 ≠ 问题消失。**
> **「我本地测了没问题」是工程界最贵的一句话。**

## 1.10 多线程（二）：可见性

### 现象：改了，但对方永远看不到

```java
static boolean flag = false;        // 注意：没有 volatile

Thread worker = new Thread(() -> {
    long loops = 0;
    while (!flag) { loops++; }
    System.out.println("[工作线程] 看到 flag = true，退出，转了 " + loops + " 圈");
});
worker.start();

Thread.sleep(1000);
flag = true;                        // 主线程改了
Thread.sleep(3000);
System.out.println("[主线程] worker.isAlive() = " + worker.isAlive());
```

输出：

```
[工作线程] 开始等 flag 变成 true ...
[主线程] 现在把 flag 改成 true
[主线程] 已经改了，等 3 秒看工作线程有没有退出
[主线程] worker.isAlive() = true          ← 永远不退出
```

加 `volatile` 之后：

```
[工作线程] 看到 flag = true，退出循环，转了 3783408775 圈
[主线程] worker.isAlive() = false
```

**同一段逻辑，一个转了 37.8 亿圈读不到，一个立刻读到。**

### 两个原因

**① JMM 工作内存模型**：每个线程有自己的工作内存（≈ 缓存/寄存器），读的是副本。

```
线程A 工作内存          主内存          线程B 工作内存
  flag=false  ←读      flag=false    写→  flag=true
      ↑
  一直读自己这份副本，主内存改了也不知道
```

**② JIT 把判断提出了循环**：`while (!flag)` 的循环体里根本没碰 `flag`，JIT 判定它不会变，于是**只读一次，之后全用寄存器**。

**这个优化本身是合法的** —— 不是 JVM 的 bug，是程序没告诉它"这个变量会被别人改"。

### `volatile` 做了什么

1. 每次读都去**主内存**读（不缓存副本）
2. **禁止把它提出循环**（禁止重排）

### ⭐ 可见性 ≠ 原子性

```java
static volatile int count = 0;
// 两个线程各 count++ 10 万次
```

实测 4 次：`191413 / 191618 / 193685 / 188817` —— **仍然丢 6315–11183**。

> **`volatile` 只管"看得见"，不管"不被打断"。`count++` 仍然是三步。**

### 三种性质

| 性质 | 含义 | 谁破坏它 | 怎么修 |
|---|---|---|---|
| **原子性** | 一步做完，不被插队 | `count++`、`i += 1` | `synchronized` / `AtomicInteger` |
| **可见性** | 一个人改了，另一个立刻看到 | JIT 缓存、CPU 缓存 | `volatile` / `synchronized` |
| **有序性** | 代码不会被打乱顺序 | 指令重排 | `volatile` / `synchronized` |

### 四种修法实测（同一份 20 万次加法）

| 写法 | 结果 |
|---|---|
| `int count`（无同步） | 丢 3–6 万 |
| `volatile int count` | 丢 6000–1 万 |
| `synchronized` | 200000，丢 0 |
| `AtomicInteger.incrementAndGet()` | 200000，丢 0 |

### `synchronized` 也能保可见性，但有条件

**必须"两边进同一把锁"。**

写方 `synchronized` 加锁、读方裸读 `while(!flag)` → 读方拿不到任何刷新保证，**照样卡死**。

> **`volatile` = 谁都能直接看到最新值。**
> **`synchronized` 的可见性 = 只在"进同一把锁的人之间"生效。**

### 都市传说："循环里加个 println 就好了"

实测：在循环里加 `System.out.println("等3秒…")`，转了 **571245** 圈就退出了。

对比 `volatile` 的 37.8 亿圈 —— **差了 6600 倍**。

两个原因：

1. 方法调用有**副作用** → JIT **不敢**把它提出循环
2. `PrintStream` 的方法是 `synchronized` → 进出锁**刷新工作内存**

**这不是修复，是碰巧。** 删掉那行 println，bug 立刻回来。

### 判断一个循环会不会被优化掉

看**循环体里有没有"副作用"**：方法调用、写字段、分配对象。

纯计算（`long t = loops % 100000000;`）就会被整段优化掉。

## 1.11 单例

### 懒汉（无锁）—— 彻底错的

```java
private static LazySingleton instance;

public static LazySingleton getInstance() {
    if (instance == null) {
        instance = new LazySingleton();
    }
    return instance;
}
```

20 个线程同时调用，**跑 5 次全部造出 20 个对象**。

> 构造器里加 `Thread.sleep(30)` 是为了把窗口放大，方便观察 —— **即使不睡，这个写法也是错的**，只是更难撞到。

### 五种写法实测对比（同样 20 线程）

| 写法 | 造出几个 | 评价 |
|---|---|---|
| 懒汉（无锁） | **20** | 错的 |
| `synchronized` 方法 | 1 | 对，但每次调用都抢锁 |
| 双重检查 DCL + `volatile` | 1 | 主流写法 |
| **静态内部类** | 1 | **推荐** |
| 饿汉 | 1 | 最简单，但没有延迟加载 |

### DCL 为什么必须加 `volatile`

`instance = new LazySingleton()` 是三步：

1. 分配内存
2. 调用构造器初始化
3. 把引用赋给 `instance`

**2 和 3 可能被重排。** 重排后，别的线程可能拿到"引用已经有值、字段还是默认值"的**半成品**。

`volatile` 禁止这次重排。

**怎么测出重排？** 光数"造了几个对象"测不出来 —— 计数器在构造器里，重排真发生了也照样是 1。

**要测必须读字段值断言**：比如给个 `int value = 100;` 的字段，别的线程读它是不是 0。

而且 x86 是 TSO 强内存模型 + `monitorexit` 屏障，**重排几乎不发生**；**ARM 上会**（飞腾就是 ARM 架构）。

> **"删掉 volatile 还是跑出 1 个"不能证明代码对，只能证明这台机器没暴露它。**

### 静态内部类为什么能保证唯一

```java
public class HolderSingleton {
    private HolderSingleton() { }

    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

JVM 保证**一个类只会被初始化一次**（`<clinit>`），而类加载过程本身是加锁的。

**而且它是延迟加载的**：不调用 `getInstance()`，`Holder` 类根本不会被加载，实例也不会创建。

### ⭐ 空着的 private 构造器有什么用

```java
private BookDaoHolder() { }        // 方法体是空的，为什么还要写？
```

**构造器的职责在修饰符，不在方法体。**

Java 规则：**一个类不写任何构造器，编译器自动送你一个 `public` 无参构造器。**

所以这一行唯一的用途是 —— **顶掉那个白送的 public 构造器**，把门关上。

至于里面的 `created++`、`sleep(30)`，那是测试探针，**生产代码要删掉**。

### 饿汉的隐藏风险

```java
private static final X INSTANCE = new X();     // 类加载时就建
```

如果构造器里连数据库、读文件：

- `<clinit>` 抛异常 → 类被标记为 **erroneous**
- 之后任何访问都抛 `NoClassDefFoundError`
- **这个类在本 JVM 里永久报废** —— 数据库恢复了也没用，只能重启进程

### 枚举单例

```java
public enum EnumSingleton {
    INSTANCE;
    public void doSomething() { }
}
```

- 天生线程安全（JVM 保证枚举实例唯一）
- **反射挡得住**：`IllegalArgumentException: Cannot reflectively create enum objects`
- 序列化也安全

## 1.12 线程池

### 为什么不能 `new Thread`

实测 2000 个任务：

| 方式 | 耗时 |
|---|---|
| 2000 个 `new Thread` | **132 ms** |
| 4 线程池 | **4 ms** |

换算：`132 ÷ 2000 ≈ 66 微秒/个` —— **这 132ms 几乎全是创建销毁开销，不是干活。**

### ⭐ 但"线程池更快"是伪命题

把任务体从 `int a = 1+1` 改成 `sleep(1)` 再跑一遍：

| | 任务体 `1+1` | 任务体 `sleep(1)` | 变化 |
|---|---|---|---|
| 2000 个 `new Thread` | 132 ms | **132 ms** | **没变** |
| 4 线程池 | 4 ms | **938 ms** | **涨 234 倍** |

**2000 个线程是同时睡的**，1ms 被 132ms 的创建开销完全淹没；**4 个线程得排队睡 500 次**。

> **线程池不让程序变快，它让并发变得可控。**

### 它真正解决的四个问题

| 问题 | 裸 `new Thread` | 线程池 |
|---|---|---|
| 资源上限 | 2000 线程 × 约 1MB 栈 → 1–2GB，`unable to create native thread` | 固定几个，内存可控 |
| 创建开销 | 每个任务 66µs | 复用，摊到接近 0 |
| 突发流量 | 线程数暴涨 → OOM | 队列缓冲 + 拒绝策略，可以主动扩 |
| 可观测性 | 不知道当前有几个在跑 | `getActiveCount()`、`getQueue().size()` |

### 七个参数

```java
new ThreadPoolExecutor(
    corePoolSize,        // 核心线程数：常驻，不干完活不会死
    maximumPoolSize,     // 最大线程数：上限
    keepAliveTime,       // 非核心线程空闲多久后销毁
    unit,                // 上面时间的单位
    workQueue,           // 任务队列
    threadFactory,       // 线程工厂：给线程起名字（排查必备）
    handler              // 拒绝策略
);
```

### 任务进来之后（顺序很重要）

```
① 当前线程数 < corePoolSize ？  → 新建核心线程，直接执行
② 队列没满 ？                  → 放进队列等着
③ 线程数 < maximumPoolSize ？   → 新建非核心线程，直接执行
④ 都满了                       → 交给拒绝策略
```

> **注意：入队在扩容之前。**
> 所以只要队列是**无界的**，第 ③ 步**永远走不到** —— `maximumPoolSize` 形同虚设。

### `newFixedThreadPool` 为什么被阿里规约禁用

```java
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(nThreads, nThreads,
        0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>());   // ← 容量 Integer.MAX_VALUE
}
```

队列永远不满 → 任务无限堆积 → **任务对象本身把内存吃光 → OOM**。

`newCachedThreadPool` 是相反的错：`maximumPoolSize = Integer.MAX_VALUE`，线程无限增长。

**生产环境一律自己 `new ThreadPoolExecutor(...)`，七个参数写清楚。**

### 四种拒绝策略（实测：核心 2、最大 2、队列 2，提交 10 个任务）

```
AbortPolicy          提交成功  4  被拒  6  真正执行  4   消失  6
CallerRunsPolicy     提交成功 10  被拒  0  真正执行 10   消失  0
DiscardPolicy        提交成功 10  被拒  0  真正执行  4   消失  6
DiscardOldestPolicy  提交成功 10  被拒  0  真正执行  4   消失  6
```

| 策略 | 行为 | 后果 |
|---|---|---|
| `AbortPolicy` | 抛 `RejectedExecutionException` | **最诚实**：提交时就失败，能接住、能记日志、能给用户报 503 |
| `CallerRunsPolicy` | 谁提交谁自己跑 | **一个都不丢**，代价是提交者被拖住 |
| `DiscardPolicy` | 静默丢掉**新来的** | **骗你**：`execute()` 不报错，任务凭空消失 |
| `DiscardOldestPolicy` | 丢掉队列里**最老的**，让位给新的 | 同上，还会**打乱提交顺序** |

> **`DiscardPolicy` 的死法最难看**：`execute()` 返回得很痛快，日志没有、异常没有、监控看到"提交成功 10 个"，实际只跑了 4 个。
> 现实中的表现："用户说下单成功了，但订单列表里没有这个订单。"

### `shutdown()` 与 `shutdownNow()`

```java
pool.shutdown();       // 不收新任务，已提交的做完，线程自动退出
pool.shutdownNow();    // 中断正在执行的，返回没跑的任务列表
```

**核心线程默认是"非守护线程（non-daemon）"，不调 `shutdown()` 程序永远不退出。**

现象：main 结束了、IDEA 控制台不显示「进程已结束」、命令行得 Ctrl+C 才停。

> **看到"程序跑完了但不退出"，先找有没有没 shutdown 的池子。**

### ⭐ 测线程池不能用 `sleep` 等

```java
// 错：测的是"某一瞬间的快照"
Thread.sleep(2000);
System.out.println("真正执行 " + executed.get());

// 对：测的是"最终结果"
pool.shutdown();
pool.awaitTermination(30, TimeUnit.SECONDS);
System.out.println("真正执行 " + executed.get());
```

**`sleep(2000)` 之后 `executed=4`，可能只是"还有 6 个没轮到"，不是"丢了 6 个"。**

凡是要统计并发程序的最终状态，都得用 `join()` / `awaitTermination()` / `CountDownLatch`，**不能用 `sleep`**。

### 线程复用的证据

核心 2、最大 4、队列 2、`CallerRunsPolicy`，提交 10 个任务：

```
任务 1 在 bookshelf-29 上执行       任务 6 在 bookshelf-32 上执行
任务 2 在 bookshelf-30 上执行       任务 7 在 main 上执行         ← 拒绝
任务 3 在 bookshelf-32 上执行       任务 8 在 bookshelf-30 上执行
任务 4 在 bookshelf-29 上执行       任务 9 在 bookshelf-31 上执行
任务 5 在 bookshelf-31 上执行       任务 10 在 main 上执行        ← 拒绝

10 个任务一共用了几个线程: 5 个 -> [bookshelf-29, bookshelf-30, bookshelf-31, bookshelf-32, main]
池内线程数: 4  队列中还剩: 0
```

**10 个任务只用了 5 个线程**，`bookshelf-29` 干了任务 1 和 4，`bookshelf-32` 干了 6 和 3 —— **这就是复用。**

这一段完整对应上面四步：① 任务 1、2 建核心线程 → ② 任务 3、4 进队列 → ③ 任务 5、6 扩容 → ④ 任务 7、10 被拒由 main 代跑。

### `Thread.sleep(n)` 的精度

`sleep(1)` 实测约 **1.88 毫秒**（938ms ÷ 2000 任务 × 4 线程）。

> **`sleep(n)` 是"至少 n 毫秒"，不是"恰好 n 毫秒"。**
> 所有限流、重试间隔、超时判断都要按"实际会比写的更长"来设计。

### `t.getId()` 的坑

返回的是**整个 JVM 里的全局线程 ID**，不是池内编号。所以你看到的是 `bookshelf-30/31/32` 而不是 1/2/3。

JDK 19 起 `getId()` 已废弃，改用 `threadId()`。要池内编号得自己维护：

```java
AtomicInteger seq = new AtomicInteger();
r -> {
    Thread t = new Thread(r);
    t.setName("bookshelf-" + seq.incrementAndGet());
    return t;
}
```

### lambda 里不能用 for 循环的 `i`

```java
for (int i = 0; i < 3; i++) {
    pool.execute(() -> System.out.println(i));   // 编译错误
}
// variable i is not effectively final
```

两种解：循环体里 `final int taskId = i;`，或者用 `AtomicInteger` 拿递增序号。

# 二、MySQL 数据库

## 2.1 建表与约束

```sql
CREATE TABLE book (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(100) NOT NULL,
    type        VARCHAR(10)  NOT NULL DEFAULT 'PAPER',
    price       DECIMAL(8,2) NOT NULL CHECK (price >= 0),
    pages       INT          NOT NULL CHECK (pages > 0),
    file_size   INT          NULL,          -- 只有电子书有，所以允许 NULL
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 字段类型选择

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 主键 | `BIGINT AUTO_INCREMENT` | 自增保证插入总在末尾，不用挪数据 |
| **钱** | `DECIMAL(10,2)` | **绝不能用 `FLOAT`/`DOUBLE`**，浮点数算不准 0.1+0.2 |
| 短文本 | `VARCHAR(n)` | n 按实际需要，别一律 `VARCHAR(255)` |
| 大文本 | `TEXT` | 不占行内空间 |
| 时间 | `DATETIME` | 与时区无关；`TIMESTAMP` 会随时区转换 |
| 布尔 | `TINYINT(1)` | MySQL 没有真正的 BOOLEAN |

**`DECIMAL(8,2)` 的含义**：总共 8 位数字，其中 2 位是小数。所以整数部分最多 6 位，最大 999999.99。

### 字符集：utf8 vs utf8mb4

**MySQL 的 `utf8` 是残废的**，最多 3 字节，存不了 emoji 和部分生僻字。
**`utf8mb4` 才是完整的 UTF-8**（4 字节）。

> **建库建表一律 `utf8mb4`。** 看到 `utf8` 就当它是历史遗留。

### 三大范式（人话版）

| 范式 | 人话 | 违反的后果 |
|---|---|---|
| 1NF | 一个格子里只能有一个值 | `authors = "刘慈欣,李淼"` 无法按作者查询 |
| 2NF | 非主键列必须依赖**整个**主键 | 联合主键 `(book_id, author_id)` 里存书名，书名只依赖 book_id |
| 3NF | 非主键列不能依赖另一个非主键列 | 存了 `出版社id` 又存 `出版社名`，改名要改几千行 |

**判断要不要拆表的正确问法**（不是"空列够多就拆"）：

> **这一列是"所有书都有的"，还是"某一类书才有的"？**

- 出版社、出版年份 —— 所有书都有 → `book` 表，`NOT NULL`
- `file_size` —— 只有电子书有 → 允许 `NULL`（或者拆子表）

### 多对多的正确建法

❌ **错误**：`book` 表加一列 `authors VARCHAR`，存 `"刘慈欣,李淼"`

三个问题：
1. 一格多值，违反 1NF
2. 没法用 SQL 查"刘慈欣写过哪些书"
3. 作者改名要改所有书

✅ **正确**：三张表

```sql
author(id, name)
book(id, name, price, ...)
book_author(book_id, author_id,
            PRIMARY KEY (book_id, author_id),
            FOREIGN KEY (book_id)   REFERENCES book(id),
            FOREIGN KEY (author_id) REFERENCES author(id))
```

**联合主键 `(book_id, author_id)` 天然去重**，同一个人同一本书插两次直接报：

```
ERROR 1062: Duplicate entry '2-1' for key 'book_author.PRIMARY'
```

## 2.2 查询

### JOIN 的四种

| 类型 | 语义 | 结果 |
|---|---|---|
| `INNER JOIN` | 两边都有才留 | 只留匹配上的 |
| `LEFT JOIN` | **左表全留**，右表没有就 NULL | 至少和左表一样多 |
| `RIGHT JOIN` | 右表全留 | 实际很少用，改成 LEFT 换位置 |
| 反连接 | `LEFT JOIN ... WHERE 右表主键 IS NULL` | 找出"没有关联"的行 |

```sql
-- 所有书 + 作者名（没有作者的书也要出现）
SELECT b.name, b.price, a.name AS author
FROM book b
LEFT JOIN book_author ba ON b.id = ba.book_id
LEFT JOIN author a       ON ba.author_id = a.id;
```

**`LEFT JOIN` 的 `WHERE` 里加右表条件会退化成 `INNER JOIN`**：

```sql
-- ✗ 写法错误：NULL 行被过滤掉了
LEFT JOIN author a ON ... WHERE a.name = '刘慈欣'

-- ✓ 条件要放 ON 里
LEFT JOIN author a ON ... AND a.name = '刘慈欣'
```

### 聚合与执行顺序

```sql
SELECT type, COUNT(*) AS 本数, AVG(price) AS 均价
FROM book
WHERE price > 10
GROUP BY type
HAVING COUNT(*) >= 2
ORDER BY 均价 DESC
LIMIT 1;
```

**执行顺序（必须背下来）**：

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

这个顺序解释了两个现象：

1. **`WHERE` 里不能用 `SELECT` 起的别名**（那时还没算出来），但 `ORDER BY` 可以
2. **`WHERE` 里不能用聚合函数**（分组还没发生），要用 `HAVING`

```
ERROR 1111: Invalid use of group function
```

### `COUNT(*)` vs `COUNT(列)`

```sql
-- 没写过书的作者，COUNT(*) 会算成 1
SELECT a.name, COUNT(*)            FROM author a LEFT JOIN book_author ba ON ... GROUP BY a.id;  -- 鲁迅 → 1 ✗
SELECT a.name, COUNT(ba.book_id)   FROM author a LEFT JOIN book_author ba ON ... GROUP BY a.id;  -- 鲁迅 → 0 ✓
```

**原理**：`COUNT(*)` 数**行**，`COUNT(列)` 数**非 NULL 值**。LEFT JOIN 没匹配到的时候，右表所有列都是 NULL。

**规则：LEFT JOIN 之后统计"右表有几条"，必须用 `COUNT(右表主键)`。**

### NULL 的坑

```sql
SELECT * FROM book WHERE file_size = NULL;    -- ✗ 永远 0 行
SELECT * FROM book WHERE file_size IS NULL;   -- ✓
```

因为 `NULL = NULL` 的结果是 `UNKNOWN`，不是 `TRUE`。**NULL 只能用 `IS NULL` / `IS NOT NULL`。**

同样的道理：`SUM` / `AVG` 会**跳过 NULL**，所以 `AVG(price)` 的分母是"非 NULL 的行数"，不是总行数。

## 2.3 索引

### 为什么快

> **索引就是把某一列排序后单独存一份，并记住每个值对应的行在哪。**
> **因为有序，才能二分。O(n) → O(log n)。**

InnoDB 用 **B+ 树**，三个关键特性：

| 特性 | 后果 |
|---|---|
| 只有叶子存数据，非叶子只存键 | 三层就能存千万级，一次查询 3 次磁盘读 |
| 叶子之间用链表相连 | 范围查询可以顺着链表扫 |
| 主键索引的叶子就是整行（聚簇索引） | 所以主键最好自增，插入总在末尾 |

### 回表与覆盖索引

```sql
SELECT * FROM book WHERE name = '活着';
```

两步：
1. 在 `name` 索引里找到 → 得到主键 `id = 1`
2. 拿 `id` **回到主键索引**取整行 ← **这叫回表**

```sql
SELECT id FROM book WHERE name = '活着';   -- 快：索引里就有 id，不回表
SELECT * FROM book WHERE name = '活着';    -- 慢：要回表
```

**如果 `SELECT` 要的列全在索引里，就不用回表，这叫「覆盖索引」。** 面试答"怎么优化这个查询"，答这个就是加分项。

### 索引失效的五种写法

| 写法 | 为什么失效 | 怎么改 |
|---|---|---|
| `WHERE YEAR(created_at) = 2026` | 对列用了函数 | `created_at >= '2026-01-01' AND < '2027-01-01'` |
| `WHERE name = 123`（name 是 VARCHAR） | **隐式类型转换** | `WHERE name = '123'` |
| `WHERE name LIKE '%活着'` | 前面有 `%` 无法二分 | 只有 `LIKE '活着%'` 能用 |
| `WHERE a = 1 OR b = 2`（b 无索引） | OR 要求两边都有索引 | 给 b 建索引，或拆成两个查询 `UNION` |
| 联合索引 `(a,b,c)` 只查 `b` | 不满足**最左前缀** | 查询条件必须从 `a` 开始 |

**最容易踩的是第二条**：`VARCHAR` 列和数字比较时，MySQL 把列转成数字再比，索引直接报废，**而且不报错**。

### 用 EXPLAIN 验证

```sql
EXPLAIN SELECT * FROM book WHERE price = 45;
```

重点看三列：

| 列 | 关注什么 |
|---|---|
| `type` | 好到差：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。**`index` 不等于 `ALL`**，见下方 |
| `key` | 实际用了哪个索引，`NULL` 表示没走索引 |
| `rows` | 预计扫多少行，越小越好 |

**`type: index` 是"扫描了整个索引树"，不是"按索引定位到几行"。但这不等于它跟全表扫差不多** —— 好不好，取决于**是否覆盖索引**：

| 情况 | `Extra` | 代价 | 和 `ALL` 比 |
|---|---|---|---|
| **覆盖**（只查索引里的列） | `Using index` | 只读索引页，索引比数据小得多 | **明显更优** |
| **不覆盖**（还要回表取其他列） | 无 | 扫索引 + 逐行随机回表 | 可能更差 |

**最有力的证据：优化器是主动选它的。** 实测（2026-11-20）：

```sql
EXPLAIN SELECT COUNT(*) FROM book;
-- type: index   key: idx_book_price   Extra: Using index    ← 优化器自己选的
EXPLAIN SELECT * FROM book;
-- type: ALL     key: NULL                                  ← 没有覆盖索引可用，只能全表扫
```

`COUNT(*)` **故意**挑最小的二级索引去扫，因为索引页远小于数据页。**如果 `type: index` 真跟 `ALL` 一样差，优化器不会在有 `ALL` 可选时选它。**

> **准确记法：`type: index` = 全索引扫描。看 `Extra` 有没有 `Using index`——有就是好方案，没有才是要优化的。**

### ⚠️ 术语纠错（2026-11-20 修正）

我原来写的是「`type: index` ≈ `ALL`，都要避免」。**这句过于绝对，是错的。**

正确的是：**它是"全索引扫描"，优劣取决于覆盖情况**。把它一律归入"要避免"，会让人不敢用 `COUNT(*)` 走最小索引这个正式优化手段。

### 索引的第二重作用：决定锁多少行 ⭐

> 这一点比"查询变快"更重要，是线上事故的高发区。

**实测结论**（3 行小表，会话 1 改 a 行，会话 2 改完全不同的 b 行）：

| 场景 | 结果 | 耗时 |
|---|---|---|
| `name` **无索引** | **ERROR 1205 锁等待超时** | 3.4 秒 |
| `name` **有索引** | 更新成功 | **0.3 秒** |

**原因**：`WHERE` 列没有索引 → 只能全表扫描 → InnoDB 在 RR 下把**扫描到的每一行都锁上**（还有间隙锁）→ **你只想改一行，结果锁了整张表。**

**生产环境的表现**：一句 `UPDATE orders SET status = ... WHERE status = '待处理'`（`status` 没索引），会把整张订单表锁死，所有写操作全部卡住。**这就是"数据库突然全员卡死、重启后又好了"的真凶。**

**结论：给经常出现在 `WHERE` / `JOIN` / `ORDER BY` 的列建索引，不只是为了快，也是为了少锁。**

### 索引的代价

- 占磁盘（等于把那列复制一份）
- **拖慢写入**：`INSERT` 一行，所有索引都要更新
- 拖慢更新：改了被索引的列，索引要重排

**经验值：一张表 5–6 个索引是正常上限。看到 20 个索引，那多半是乱建的。**

## 2.4 事务

### 为什么需要

张三转李四 100 块，两条 SQL：

```sql
UPDATE account SET balance = balance - 100 WHERE name = '张三';
UPDATE account SET balance = balance + 100 WHERE name = '李四';
```

第一条执行完、第二条没执行时断电 → **张三少了 100，李四没收到，钱凭空消失。**

### 三个命令

```sql
START TRANSACTION;   -- 开始打包（也可以写 BEGIN）
  ...SQL...
COMMIT;              -- 确认，全部生效
-- 或
ROLLBACK;            -- 反悔，全部撤销
```

### 最反直觉的现象

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 300 WHERE name = '张三';
SELECT * FROM account;    -- 显示 700（你自己看得见）
ROLLBACK;
SELECT * FROM account;    -- 变回 1000
```

> **事务里做的修改，只有你自己看得见。别人看不见，磁盘上也不算数。直到 COMMIT 才落地。**

### ACID

| 字母 | 英文 | 意思 | 转账场景 |
|---|---|---|---|
| **A** | Atomicity 原子性 | 要么全做，要么全不做 | 不会出现扣了张三、没加李四 |
| **C** | Consistency 一致性 | 数据从一个合法状态到另一个合法状态 | 转账前后总额必须都是 1500 |
| **I** | Isolation 隔离性 | 并发事务互不干扰 | 后一个事务必须等前一个结束 |
| **D** | Durability 持久性 | 提交了就一定不丢 | `COMMIT` 返回后，断电也不丢 |

### ⚠️ 最重要的陷阱：MySQL 只回滚"出错的那一条"

**实测结果**（初始：张三 50，李四 500，总额 550）：

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE name = '张三';  -- ERROR 3819 CHECK 约束失败
UPDATE account SET balance = balance + 100 WHERE name = '李四';  -- Query OK，照常执行
COMMIT;
```

| | 张三 | 李四 | 总额 |
|---|---|---|---|
| 转账前 | 50 | 500 | **550** |
| 转账后 | 50 | **600** | **650** |

**凭空多了 100 块。**

**原因（分两层，缺一不可）**：

1. **引擎层**：语句失败时，InnoDB **只回滚出错的那一条语句**，事务本身仍然活着，它不会自动帮你 `ROLLBACK` 整个事务。
2. **客户端层**：**得有人继续把后续语句发出去**。交互式敲命令会继续；`mysql` 批量模式默认遇错即停（要加 `-f` 才继续）；JDBC 里异常一抛、连接一关，未提交的事务就整个回滚了。

两条同时成立，才会"凭空多 100"。**2026-11-20 复核实测：**

| 执行方式 | 张三 | 李四 | 总额 |
|---|---|---|---|
| 批量执行、不加 `-f`（遇错停止） | 50 | 500 | **550**（没变化） |
| 批量执行加 `-f`（等价交互式继续） | 50 | **600** | **650**（凭空多 100） |

> ⚠️ 注意：**PostgreSQL 不是这样**。PG 一旦出错，整个事务作废，后面语句全报 `current transaction is aborted`。**MySQL 不会 —— 所以这里更容易踩坑。**

**结论**：

> **数据库不知道你这两条 UPDATE 是一件事。"它们必须一起成功"这个判断，只能由写代码的人来做。**

### 正确写法（记住这段模板）

```java
conn.setAutoCommit(false);      // 等于 START TRANSACTION
try {
    // 一堆 SQL
    conn.commit();
} catch (Exception e) {
    conn.rollback();            // 任何一步出错，全部撤销
    throw e;
}
```

### 持久性靠 redo log，不是"数据已写盘"

`COMMIT` 返回的一瞬间，数据页**很可能还在内存里**（buffer pool），没落盘。

```
1. 改内存里的数据页                    ← 快，但断电就没了
2. 把"改了哪行、改成什么"写进 redo log，fsync 到磁盘   ← COMMIT 返回前必须完成
3. 空闲时再把内存页慢慢刷到磁盘
```

断电重启后，MySQL 读 `redo log` **重放**这些操作，数据就回来了。

> **这叫 WAL（Write-Ahead Logging，预写日志）。**
> **COMMIT 返回时，日志已经落盘，但数据本身没有。持久性靠的是日志。**

正因为只需顺序写一条日志（而不是等随机写数据页），MySQL 才能做到每秒几千次提交。

### 事务要短

事务从 `START TRANSACTION` 到 `COMMIT` 之间一直持有锁。**事务里不要等用户输入、不要调外部接口。**

> 真实事故里一大类叫"长事务把数据库拖死"：一个人开了事务忘了提交，几小时后全系统的写操作卡死。

排查工具：

```sql
SELECT trx_id, trx_state, trx_started, trx_isolation_level,
       trx_rows_modified, trx_query
FROM information_schema.INNODB_TRX;
```

**线上"突然变慢、写入全卡"的第一步排查，就是看这里有没有开了几小时的事务。**

## 2.5 隔离级别

### 三种并发问题

| 现象 | 一句话 | 比喻 |
|---|---|---|
| **脏读** dirty read | 读到别人**还没提交**的数据 | 别人改了草稿还没保存，你就照着抄了 |
| **不可重复读** non-repeatable read | 同一事务里读同一行，**两次不一样** | 你抄第一页，他改了第二页，回头对不上 |
| **幻读** phantom read | 同一事务里查同一范围，**行数不一样** | 你数了 5 份文件，他塞进 1 份，你再数是 6 份 |

> **不可重复读改的是同一行；幻读多出来的是新行。** 这是唯一的区别，也是面试最爱考的那一句。

### 四个档位

| 级别 | 脏读 | 不可重复读 | 幻读 | 默认在哪 |
|---|---|---|---|---|
| `READ UNCOMMITTED` | 会 | 会 | 会 | 没人用 |
| `READ COMMITTED` | 不会 | 会 | 会 | Oracle / PostgreSQL |
| `REPEATABLE READ` | 不会 | 不会 | InnoDB 基本不会 | **MySQL** |
| `SERIALIZABLE` | 不会 | 不会 | 不会 | 几乎不用 |

```sql
-- 只影响下一个事务
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
START TRANSACTION;
```

> **`SET TRANSACTION` 必须在 `START TRANSACTION` 之前执行。**

### 实测：三种现象的样子

| 实验 | 看到的现象 |
|---|---|
| 脏读（RU） | 李四 500 → **1500**（对方未提交）→ 对方 ROLLBACK 后回 500 |
| 不可重复读（RC） | 同一事务内 500 → **600** |
| RR 快照 | 同一事务内 700 → **700**，`COMMIT` 之后才是 800 |
| 幻读（RR） | `SELECT COUNT(*)` 两次都是 **2**，但 `UPDATE 王五` 返回 **`Rows matched: 1`** |

**最后一行是幻读最精确的样子**：

```
SELECT COUNT(*) FROM account;                          → 2
UPDATE account SET balance = balance WHERE name = '王五';
→ Query OK, 0 rows affected
  Rows matched: 1   Changed: 0   Warnings: 0
```

**`SELECT` 说 2 行，`UPDATE` 说匹配到 1 行。** 同一条记录，在同一个事务里，"看不见"却"摸得到"。

### MVCC：MySQL 靠"记旧版本"而不是"锁"

```
李四 balance 这一行：
  版本1: 500  ← B 的事务开始时就绑定了这个版本
  版本2: 600  ← A 改出来的
  版本3: 700  ← A 又改了一次
```

B 的 `SELECT` 永远读"我事务开始时有效的那个版本"。

> **妙处在于：读不加锁，写不阻塞读。** A 在改，B 在念旧版本，互不干扰。

`REPEATABLE READ` 靠"记住旧版本"，不是靠"锁住"。

### 幻读为什么"基本"解决了

InnoDB 在 RR 下给 `UPDATE ... WHERE 范围` 加了**间隙锁（Gap Lock）**：不只锁匹配的行，还锁住行与行之间的"缝隙"，让别人插不进来。

而普通 `SELECT`（快照读）看不到新插入的行，所以幻读在 MySQL 的 RR 下**大部分场景**被堵住了 —— 但**快照读看不见、当前读（UPDATE/DELETE）看得见**，这就是上表最后一行那个 `2` 和 `1` 的矛盾。

### 为什么 MySQL 默认 RR

1. **MVCC 让 RR 的代价很小**：读不加锁，隔离性提升不额外变慢
2. **主从复制**：老版本 `binlog` 用 `STATEMENT` 格式时，`READ COMMITTED` 会导致主从不一致
3. **历史惯性**

**反面**：用 Seata 这类分布式事务框架时，很多要求 `READ COMMITTED`（需要在事务里看到最新已提交数据），**得手动改。**

# 三、JDBC

## 3.1 JDBC 是什么

> **JDBC 是 Java 官方定的一套"访问数据库"的接口。各数据库厂商（MySQL / Oracle / PostgreSQL）自己提供实现 —— 就是那个驱动 jar。**

好处：`Connection`、`Statement`、`ResultSet` 这些名字**全行业统一**，换数据库只改 URL 和 jar。

**面试标准答案**："Java 访问数据库的标准规范，由各数据库厂商提供驱动实现。"

## 3.2 五个步骤

| 步骤 | 代码 | 说明 |
|---|---|---|
| 1 拿连接 | `DriverManager.getConnection(url, user, pwd)` | url 里写清楚连哪个库 |
| 2 造语句 | `conn.prepareStatement(sql)` | 几乎永远用这个，不用 `createStatement` |
| 3 执行 | `ps.executeQuery()` / `ps.executeUpdate()` | 查 vs 增删改 |
| 4 取数据 | `while (rs.next()) { rs.getString("name") }` | 游标一开始在**第一行之前** |
| 5 关闭 | try-with-resources 自动 | 顺序与打开相反 |

**第 4 步是新手最常错的**：`ResultSet` 不是"装着数据的列表"，是**一根光标**。必须调 `next()` 才能移到第一行。

## 3.3 URL 拆解

```
jdbc:mysql://localhost:3306/bookshelf?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=utf8
└┬─┘└─┬─┘  └───┬───┘└┬─┘└───┬────┘└──────────────────────┬───────────────────────────────────────────┘
 │    │        │     │      │                          └─ 参数（用 & 分隔）
 │    │        │     │      └─ 数据库名
 │    │        │     └─ 端口
 │    │        └─ 主机
 │    └─ 子协议（哪个厂商）
 └─ 协议永远是 jdbc
```

| 参数 | 不写会怎样 |
|---|---|
| `useSSL=false` | 8.0 会刷一堆警告 |
| `serverTimezone` | **时间类型差 8 小时** |
| `characterEncoding=utf8` | 中文可能乱码 |

## 3.4 驱动加载

```java
Class.forName("com.mysql.cj.jdbc.Driver");   // 老写法，现在可以省
```

**JDBC 4.0（Java 6）以后不需要了** —— 驱动 jar 里有 SPI 配置文件，`DriverManager` 会自动找到。

**面试完整答案**：JDBC 4.0 之前必须 `Class.forName` 显式加载；之后靠 SPI 自动加载，可以不写。

## 3.5 SQL 注入 ⭐

### 漏洞代码

```java
String sql = "SELECT id, name, price FROM book WHERE name = '" + input + "'";
```

用户输入 `' OR '1'='1`，拼出来：

```sql
SELECT id, name, price FROM book WHERE name = '' OR '1'='1';
```

**实测结果：整张表 4 行全部返回。**

### 数引号就明白了

```
name = ''  OR  '1'='1'
        ↑↑
        用户输入的第一个引号把字符串提前关掉了
```

- `name = ''` → 找名字为空的书 → 没有
- `OR '1'='1'` → **永远为真**

> **SQL 注入的本质：你以为是"用户输入了一个值"，数据库却以为"用户输入了一段逻辑"。**
> **数据变成了代码。**

### 更狠的：UNION 读别的表

```sql
-- 攻击者输入：' UNION SELECT id, name, balance FROM account --
SELECT id, name, price FROM book WHERE name = '' UNION SELECT id, name, balance FROM account;
```

**实测结果**：返回的是 `account` 表的 3 行（张三 / 李四 / 王五），`balance` 被硬塞进了 `price` 列。

**你想查一本书，结果把别人账户余额查出来了。**

### 登录绕过（最经典）

```java
"SELECT * FROM user WHERE username = '" + name + "' AND password = '" + pwd + "'"
```

用户名输入 `' OR '1'='1' --`：

```sql
SELECT * FROM user WHERE username = '' OR '1'='1' --' AND password = '...'
```

`--` 是 SQL 注释符，**后半段密码校验被整行注释掉了**。查询恒真 → 登录成功。

### 防御：PreparedStatement

```java
String sql = "SELECT id, name, price FROM book WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, input);      // 无论输入什么，都只是"一个值"
ResultSet rs = ps.executeQuery();
```

**同样的注入串，这次返回 `共 0 行`** —— 它只是一个查不到的书名。

### 为什么安全：结构先定死

```
Statement：
  拼出一整条字符串 → 发给 MySQL → MySQL 当成语法解析  ← 危险在这里

PreparedStatement：
  1. 先发模板 "WHERE name = ?"
  2. MySQL 解析它，生成执行计划，结构固定
  3. 再把参数值单独发过去
  4. MySQL 把值填进洞里 —— 它永远只是【值】
```

> **PreparedStatement 的本质不是"把危险字符转义掉"，而是根本不给你"把数据变成语法"的机会。**

### 三个坑

**① `?` 下标从 1 开始**

```java
ps.setString(1, input);   // 第一个问号
```

报错 `Parameter index out of range (0 < 1)` 就是这个。

**② `?` 只能替换值，不能替换表名/列名/ORDER BY 字段**

```java
"SELECT * FROM ? WHERE ? = ?"     // ✗ 语法错误
"ORDER BY ?"                      // ✗ 没用
```

**表名列名属于"结构"，发送模板时就必须确定。** 排序字段必须走白名单：

```java
String column = switch (input) {
    case "price" -> "price";
    case "pages" -> "pages";
    default -> "id";
};
```

> **面试追问："PreparedStatement 能防所有注入吗？"**
> **答：不能。表名、列名、ORDER BY 这些标识符位置它管不到，必须自己做白名单校验。**

**③ `executeQuery` vs `executeUpdate`**

```java
ResultSet rs = ps.executeQuery();    // 查，返回结果集
int rows = ps.executeUpdate();       // 增删改，返回影响行数
```

用错不报错，只是拿到一个没用的对象。

## 3.6 DAO 分层

### 为什么要分

改造前 `Main.java` 里同时有 SQL、`System.out.println`、`Scanner`，150 行里改一处要读完全文。

**DAO = Data Access Object。只负责"数据存在哪、怎么取"，不管"取来干什么"。**

```java
public class BookDao {
    private static final String URL = "jdbc:mysql://localhost:3306/bookshelf?...";
    private static final String USER = "root";
    private static final String PASSWORD = "123456";

    private Connection getConnection() throws SQLException {
        return DriverManager.getConnection(URL, USER, PASSWORD);
    }

    public List<Book> findAll() { ... }
    public Book findById(long id) { ... }
    public long insert(Book book) { ... }
    public int update(Book book) { ... }
    public int deleteById(long id) { ... }
    public int count() { ... }

    private Book toBook(ResultSet rs) throws SQLException { ... }   // 行 → 对象
}
```

**`toBook()` 就是 ORM 在底下干的事。** 以后用 MyBatis / JPA，就是把这段手写映射换成配置。

### 自查判据

- `Main.java` 里搜 `SELECT` / `Connection` / `PreparedStatement` / `ResultSet` / `jdbc:mysql` —— **应该一个都没有**
- `BookDao.java` 里不该有 `System.out.println` 和 `Scanner`

两边都满足，才算真的分开了。

### 三次连接的问题

```java
Book a = dao.findById(1);     // 一次连接
Book b = dao.findById(2);     // 一次连接
dao.update(a);                // 一次连接
```

慢是小事（TCP 三次握手 + 认证的开销远大于一条 SELECT）。

**要命的是：三次连接 = 三个独立事务，无法同生共死。**

批量插入时第 2 个失败、第 1 个已提交，**撤不回来**。SQL 课学的 `START TRANSACTION` 在这一层根本用不上。

正确解法是连接池（HikariCP），但那是后面的事。

### SQLException 是受检异常

```java
catch (SQLException e) {
    throw new RuntimeException("查询失败", e);    // ← 第二个参数必须传
}
```

传第二个参数（cause）才能**保留根因**，否则 `Caused by:` 那一段就没了，排查时看不到真正的错误。

## 3.7 BigDecimal 与金额

### 为什么不能用 int / double

数据库 `DECIMAL(8,2)` 存 `19.90`，Java 用 `int` 接 → 读成 `19`。

**静默丢精度，不报错。**

### 三条铁律

```java
// 1. 不能 == 和 < >，必须 compareTo
a.compareTo(b) == 0
a.compareTo(BigDecimal.ZERO) < 0

// 2. 不能用 + - * /，要用方法
a.add(b);  a.subtract(b);  a.multiply(b);
a.divide(b, 2, RoundingMode.HALF_UP);      // 除法必须给精度和舍入，否则可能抛异常

// 3. 构造优先用字符串
new BigDecimal("0.1")     // 精确 0.1
new BigDecimal(0.1)       // 0.1000000000000000055511151231257827
```

### ⭐ scale 的坑

```java
new BigDecimal("25").toString();      // "25"      scale = 0
new BigDecimal("25.00").toString();   // "25.00"   scale = 2

a.equals(b);        // false    ← equals 连 scale 一起比
a.compareTo(b);     // 0        ← compareTo 只比数值
```

现象：更新后打印 `围城,25元`，重新查出来变成 `围城,25.00元`。

**修法：显示前统一 `price.setScale(2, RoundingMode.HALF_UP)`。**

### `toString()` 里不要有副作用

```java
// 错：改了自己的字段
public String toString() {
    price = price.setScale(2, RoundingMode.HALF_UP);       // ← 副作用
    return name + "," + price + "元," + pages + "页";
}

// 对：只算，不改
public String toString() {
    return name + "," + price.setScale(2, RoundingMode.HALF_UP) + "元," + pages + "页";
}
```

**`toString()` 会被日志、调试器、`+` 拼接随时调用，必须是纯函数。**

## 3.8 主键 id 与 `getGeneratedKeys()`

### 属性 vs 身份

| | `name` | `id` |
|---|---|---|
| 是什么 | **属性**：会变、会重复 | **身份**：永不变、唯一 |
| 能不能拿来定位一条记录 | 不能 | 能 |

**踩过的坑**：加两本同名《围城》（10 元 / 12 元），数据库里有 id 11 和 12，但 Java 的 `Book` 没有 id 字段，`dao.delete("围城")` **一次删掉两本**。

> **`DELETE FROM book WHERE name = ?` 是在说"所有叫这个名字的都删掉"。**
> **你原来想说的是"删掉第 11 本"。**

### 读出 id

```java
private Book toBook(ResultSet rs) throws SQLException {
    long id = rs.getLong("id");                    // ← 先读出来
    String name = rs.getString("name");
    ...
    Book book;
    if ("EBOOK".equals(type)) {
        book = new EBook(name, price, pages, fileSize);
    } else {
        book = new PaperBook(name, price, pages);
    }
    book.id = id;                                  // ← 再赋进去
    return book;
}
```

**`id` 不放进构造器** —— 新书还没入库，哪来的 id？用 `0` 表示"未入库"。

### 拿新生成的 id

```java
String sql = "INSERT INTO book(name, type, price, pages, file_size) VALUES (?,?,?,?,?)";

try (Connection conn = getConnection();
     PreparedStatement ps = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {

    ps.setString(1, book.getName());
    ps.setString(2, book.getType().equals("电子书") ? "EBOOK" : "PAPER");
    ps.setBigDecimal(3, book.price);
    ps.setInt(4, book.pages);
    if (book instanceof EBook ebook) ps.setInt(5, ebook.fileSize);
    else                             ps.setNull(5, Types.INTEGER);

    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            book.id = keys.getLong(1);             // ← 回填到对象上
        }
    }
    return book.id;
}
```

### ⭐ 为什么不能用 `SELECT MAX(id)`

**并发下会拿到别人的 id：**

```
会话 A：INSERT 一本书      → 得到 id 11
会话 B：INSERT 另一本书    → 得到 id 12
会话 A：SELECT MAX(id)     → 拿到 12  ← 那是 B 的书！
会话 A：用 12 去 UPDATE    → 改了别人的数据
```

**第二个失效**：事务回滚后，自增 id 已经被消耗掉了（`AUTO_INCREMENT` 不回收），`MAX(id)` 和实际分配对不上。

### `getGeneratedKeys()` 为什么并发安全

它底层是 MySQL 的 `LAST_INSERT_ID()`，这个值是**连接级**的 —— 每个连接各记各的，**互不干扰**。

### AUTO_INCREMENT 断号不是 bug

删掉 id 12 之后，下一条新记录会是 13，不是 12。

**这是保护**：id 复用会让所有历史引用（日志、订单、外部系统）指向错的东西。

### `LIMIT 1` 是一个承诺

`findByName` 原来带 `LIMIT 1`，那是**基于 "name 唯一" 这个承诺**。

现在 name 不唯一了，**这个承诺就是谎言** —— 它会静默返回错误的那一本。

三种改法：

| 改法 | 语义 |
|---|---|
| 返回 `List<Book>` | 诚实：有几本就返回几本 |
| `existsByName()` 保留 `LIMIT 1` | 只问"有没有"，不关心是哪本 |
| `findFirstByName()` | 名字里就写明"只取第一本" |

## 3.9 update 与列清单

### update 是整行覆盖

```java
UPDATE book SET name=?, type=?, price=?, pages=?, file_size=? WHERE id=?
```

**少 bind 一个参数，那个字段就被写坏**（NULL 或 0）。

`ps.setLong(6, book.id)` 漏写 → `WHERE id = 0` → 影响 0 行，**不报错，静默失败**。

**所以调用方必须检查返回值**，而且必须**先 `findById` 拿到完整对象**，改一个字段再整体写回 —— 否则会把没改的字段一起写坏。

### ⭐ 列清单散落的坑

同一个 6 列清单在 4 个方法里各写一遍，加 `id` 时漏改两处：

| 位置 | 问题 | 报错 |
|---|---|---|
| `findById` 的 `SELECT` | 少了 `type` | `Column 'type' not found` |
| `findByName` 的 `SELECT` | 少了 `id` | `Column 'id' not found` |
| `update` 的 `UPDATE` | 只有 4 个 `?`，却 bind 了 6 个 | `Parameter index out of range` |

**修法：抽常量，让列清单只声明一次。**

```java
private static final String COLS = "id, name, type, price, pages, file_size";
```

### ⭐ 空格 bug（SQL 拼接最阴的一种）

```java
String sql = "SELECT " + COLS + "FROM book ORDER BY id";
// 拼出来是：... pages, file_sizeFROM book ORDER BY id
```

报错却是：

```
Unknown column 'id' in 'field list'
```

**指向的词不是写错的那个词。**

原因：MySQL 把 `file_sizeFROM` 当成列名，把 `book` 当成它的**别名**，`FROM` 子句整个消失了。

验证：

```sql
SELECT 1 book;                        -- 列头就叫 book，book 是别名
SELECT 1 book ORDER BY id;            -- ERROR 1054: Unknown column 'id' in 'order clause'
```

**防复发写法**：把 `FROM` 也放进常量。

```java
private static final String SELECT_ALL = "SELECT id, name, type, price, pages, file_size";
String sql = SELECT_ALL + " FROM book ORDER BY id";
```

### 错误栈怎么读

```
Exception in thread "main" java.lang.RuntimeException: 查找图书时出错
    at BookDao.findById(BookDao.java:182)          ← 包装层，你抛的
Caused by: java.sql.SQLException: Column 'type' not found.
    at ...                                          ← 真正的错
```

> **`at ...` 是"在哪被抛出"，`Caused by` 才是"错的是什么"。**
> 两者看起来冲突时，**永远以 `Caused by` 为准`。**

### 运行时错误 ≠ 编译错误

| | 编译错误 | 运行时错误 |
|---|---|---|
| 谁报的 | `javac` / IDEA 红波浪线 | JVM，跑起来才炸 |
| 例子 | 类型不兼容、漏分号 | `ERROR 1146 Table doesn't exist`、`ClassCastException` |
| 能不能跑起来 | 跑不起来 | **能跑，跑到那一行才崩** |

`ERROR 1146`、`ERROR 1054` 全是**运行时**错误 —— 数据库的报错永远只能在运行期出现。

# 四、对比表总汇

## 4.1 语言与数据库对比表

| 对比项 | A | B |
|---|---|---|
| `==` | 比较引用/值 | `equals` 比较内容 |
| 重载 | 同类内，参数不同 | 重写：父子类，签名相同 |
| 抽象类 | `extends` 单继承，可有字段和实现 | 接口：`implements` 多实现，只能有常量 |
| `ArrayList` | 数组，随机访问 O(1)，插入删除 O(n) | `LinkedList`：链表，插入 O(1)，随机访问 O(n) |
| `ArrayList.remove(1)` | 删下标 1 | `remove(Integer.valueOf(1))` 删元素 1 |
| `COUNT(*)` | 数行 | `COUNT(列)` 数非 NULL 值 |
| `WHERE` | 分组前过滤，不能聚合 | `HAVING`：分组后过滤，可以聚合 |
| `INNER JOIN` | 只留匹配的 | `LEFT JOIN`：左表全留 |
| 聚簇索引 | 主键索引，叶子是整行 | 二级索引：叶子是主键值，要回表 |
| `type: ref` | 走索引，好 | `type: ALL/index`：全扫，要优化 |
| `READ COMMITTED` | Oracle / PG 默认 | `REPEATABLE READ`：MySQL 默认 |
| `COMMIT` | 日志落盘，数据未必 | `ROLLBACK`：全部撤销 |
| `Statement` | 字符串拼接，可注入 | `PreparedStatement`：参数化，安全 |
| `executeQuery` | 返回 `ResultSet` | `executeUpdate`：返回 `int` |

## 4.2 并发与泛型对比表

| 对比项 | A | B |
|---|---|---|
| `volatile` | 保可见性、禁重排，**不保原子性** | `synchronized`：三者都保，但会阻塞 |
| `synchronized void m()` | 锁 `this`，每对象一把 | `static synchronized`：锁 `Xxx.class`，全 JVM 一把 |
| `count++` | 读-加-写三步，非原子 | `AtomicInteger.incrementAndGet()`：原子 |
| 可见性 | 一个人改了另一个立刻看到 | 原子性：一步做完不被打断 |
| `volatile` 的可见性 | **谁都能看到最新值** | `synchronized` 的可见性只在"进同一把锁的人之间"生效 |
| 懒汉单例（无锁） | 20 线程造 **20 个对象** | 静态内部类 / 枚举：唯一 |
| `t.run()` | 普通方法调用，在当前线程跑 | `t.start()`：启动新线程 |
| `Thread.sleep(n)` | **至少** n 毫秒（实测 1ms ≈ 1.88ms） | —— |
| `shutdown()` | 做完手上的再退出 | `shutdownNow()`：中断，返回未跑的任务 |
| `AbortPolicy` | 抛异常，**最诚实** | `DiscardPolicy`：静默丢弃，最危险 |
| `newFixedThreadPool` | 无界队列，`maximumPoolSize` 失效 | `newCachedThreadPool`：线程数无上限 |
| 真泛型 | 编译器拦住，字节码擦除 | 假泛型：声明 `<T>` 却全用 `Object` |
| `getGeneratedKeys()` | 连接级 `LAST_INSERT_ID()`，并发安全 | `SELECT MAX(id)`：并发下会拿到别人的 id |
| `BigDecimal.equals` | **连 scale 一起比** | `compareTo`：只比数值 |
| `LIMIT 1` | 承诺"只有一条" | `List<Book>`：诚实返回多条 |

# 五、常见错误码

| 错误码 | 含义 | 常见原因 |
|---|---|---|
| **1045** | Access denied | 密码错 / 用户无权限 |
| **1048** | Column cannot be null | 插了 NULL 到 NOT NULL 列 |
| **1054** | Unknown column | 列名拼错 / 别名用错（如 `a.name` 但没定义 a） |
| **1062** | Duplicate entry | 主键/唯一索引冲突 |
| **1064** | SQL syntax error | 少逗号 / 少 `ON` / 多条语句混在一起 |
| **1111** | Invalid use of group function | 在 `WHERE` 里用了聚合函数，应该用 `HAVING` |
| **1146** | Table doesn't exist | 表名拼错 / 没 `USE 库名` |
| **1205** | Lock wait timeout exceeded | 别的事务长时间持锁；或 UPDATE 没走索引锁了全表 |
| **1213** | Deadlock found | 两个事务互相等对方的锁 |
| **3819** | Check constraint violated | 违反 `CHECK` 约束（如价格为负） |

### Java 侧的运行时异常

| 异常 | 含义 | 常见原因 |
|---|---|---|
| `ClassCastException` | 类型转换失败 | 用了 `Object` 容器（假泛型） |
| `NumberFormatException` | 字符串转数字失败 | `Integer.parseInt("abc")` |
| `NullPointerException` | 对 null 调用方法 | 忘了判空；`HashMap.get()` 找不到返回 null |
| `ConcurrentModificationException` | 遍历时修改集合 | for 循环里 `remove` |
| `IllegalArgumentException: Cannot reflectively create enum objects` | 反射造枚举 | 枚举单例自带保护 |
| `RejectedExecutionException` | 线程池拒绝 | 队列和线程都满了（`AbortPolicy`） |
| `NoClassDefFoundError` | 类初始化失败过 | `<clinit>` 抛过异常，该类在本 JVM 永久报废 |
| `OutOfMemoryError: unable to create native thread` | 线程开太多 | 每个线程约 1MB 栈 |

**遇到错误的第一反应**：**先读完整报错，不要猜。** 报错里几乎总是写清楚了表名、列名、行号。

## 6.1 Java 阶段

| 坑 | 现象 | 教训 |

## 6.2 Git 阶段

| 在 mysql 客户端里跑 `mysqldump` | `Unknown command '\U'` | `mysqldump` 是**独立的命令行工具**，不是 SQL |

## 6.3 MySQL 阶段

| 坑 | 现象 | 教训 |
|---|---|---|
| 把报错文本当命令粘回去 | `ERROR 1064` + `->` 续行状态 | 卡在 `->` 时按 `\c` 取消 |
| `SELECT a.name COUNT(...)` | 1064 | 两列之间**少逗号** |
| `LEFT JOIN ba a.id = ba.author_id` | 1064 | **少 `ON`** |
| 自己发明了 `price` 表 | `Table 'bookshelf.price' doesn't exist` | 先确认表名 |
| 用 `bookname` 当关联键 | 作者改名后关联失效 | **用自增 id 当外键** |
| 忘了插"鲁迅" | 聚合结果少一行，坑没踩到 | 实验的数据必须齐 |
| `HAVING COUNT(*) > 2` | `Empty set` | 中文"2 本以上"**包含 2**，要 `>=` |
| `SELECT` 用 `COUNT(列)`、`HAVING` 用 `COUNT(*)` | 数据一变就自相矛盾 | **两处必须用同一个表达式** |
| `LEFT JOIN` 的 `WHERE` 加右表条件 | 退化成 INNER JOIN | 条件放 `ON` 里 |
| 脏读实验"没出现" | 以为隔离级别没生效 | **窗口 A 的 UPDATE 根本没执行**（截图里没有 `Query OK`） |
| `UPDATE` 锁了整张表 | 另一个窗口改**别的行**也报 1205 | **`WHERE` 列没索引 → 全表扫描 → 锁全部行** |

## 6.4 最有价值的三个"意外"

**① 钱凭空多了 100 块**

`START TRANSACTION` 里第一条 UPDATE 报 CHECK 约束失败，第二条照样执行，`COMMIT` 后总额从 550 变 650。

→ **MySQL 只回滚出错的那一条语句，不回滚整个事务。**

**② `SELECT COUNT(*)` 说 2，`UPDATE` 说 `Rows matched: 1`**

幻读最精确的样子：快照读看不见的行，当前读摸得到。

→ **MVCC 给读操作的是"旧版本"，UPDATE 用的是"最新版本"。**

**③ 没索引的 UPDATE 锁了整张表**

改一行，锁全表，另一个窗口改无关的行也超时。

→ **索引不只决定"读多少行"，还决定"锁多少行"。**

## 6.5 Java 进阶阶段（DAO / 泛型 / 反射）

| 坑 | 现象 | 教训 |
|---|---|---|
| `SELECT " + COLS + "FROM` | `Unknown column 'id' in 'field list'` | **少一个空格 → 表名被当成列名别名 → FROM 子句消失** |
| 列清单在 4 个方法里各写一遍 | 加 `id` 后三处报错 | 抽 `COLS` 常量，**只声明一次** |
| `SELECT` 少一列 | `Column 'type' not found` | 看栈要看 `Caused by`，不看 `at` |
| `UPDATE` 4 个 `?` 却 bind 6 个 | `Parameter index out of range` | **占位符个数必须与 bind 个数相等** |
| `UPDATE` 漏 `setLong(6, id)` | 影响 0 行，不报错 | **调用方必须检查返回值** |
| `int` 接 `DECIMAL(8,2)` | 19.90 变成 19 | 金额一律 `BigDecimal` |
| `toString()` 里给字段赋值 | 打印一次就改了数据 | **`toString()` 必须是纯函数** |
| `BigDecimal(25).equals(BigDecimal("25.00"))` | `false` | `equals` 比 scale，比较数值用 `compareTo` |
| 用 `name` 当删除条件 | 一次删掉两本同名书 | **name 是属性，id 才是身份** |
| `SELECT MAX(id)` 拿新 id | 并发下拿到别人的 id | 用 `getGeneratedKeys()`（连接级） |
| `Box<T>` 里全用 `Object` | `Object 无法转换为 Book` | 判据：塞个 `String`，编译报错才是真泛型 |
| 注解忘了 `@Retention(RUNTIME)` | 反射 `isAnnotationPresent` 永远 false | **默认值是 `CLASS`，静默失效** |
| 反射读不到注解就以为"private 改不了" | 排查方向全错 | 先看 `if` 条件有没有成立，再看权限 |

## 6.6 并发阶段最有价值的四个"意外"

**① 代码里明明写了 `synchronized`，还是丢数据**

数据是 `static int count`，方法却是 `synchronized void add()`（漏了 static）。两个线程各 new 一个对象 → **各拿各的锁**。

实测丢 6367–13690。

→ **锁必须锁在"被保护的那份数据"上。数据是 static 的，锁就必须是 static 的。**

**② 转了 37.8 亿圈也读不到那次修改**

`while (!flag)` 没有 `volatile`，JIT 把它提出了循环；主线程改了 `flag = true`，工作线程永远看不见。

加 `volatile` 后立刻退出。

→ **能修改别人正在等的变量，必须 `volatile`（或两边同一把锁）。**

**③ 加了 `volatile` 还是丢 6000–10000**

`volatile int count` 两线程各 `count++` 10 万次，4 次结果全错。

→ **可见性 ≠ 原子性。`volatile` 只管"看得见"，不管"不被打断"。**

**④ `DiscardPolicy` 下 10 个任务静默消失 6 个**

```
提交成功 10, 被拒 0, 真正执行 4
```

`execute()` 没有任何异常，日志没有任何警告。

→ **一个 API 说"成功"，和一件事"做成了"，是两件完全不同的事。**

# 七、面试问答速查

> 用法：先看问题，**用嘴说出来**，说不出来再看下面的要点。

### Java

**Q1. 面向对象的三大特性？**
封装（隐藏细节，保护不变量）、继承（复用+扩展）、多态（同一接口不同实现）。

**Q2. 重载和重写的区别？**
重载在同一个类里，方法名相同参数不同；重写在父子类之间，签名完全相同。重写有三级限制：权限不能变小、不能抛更宽的受检异常、`static` 不能被重写。

**Q3. 抽象类和接口的区别？**
抽象类表达"是什么"，单继承，可以有字段和构造器；接口表达"能做什么"，多实现，只能有常量。Java 8 后接口可以有 `default` 方法。

**Q4. `==` 和 `equals` 的区别？**
`==` 比较引用地址（基本类型比较值），`equals` 比较内容。比较内容永远用 `equals`。

**Q5. 为什么重写 `equals` 必须重写 `hashCode`？**
契约要求 `equals` 相等的对象 `hashCode` 必须相等。否则在 `HashMap` 里会被放进不同的桶，导致 `get()` 找不到。

**Q6. `HashMap` 的底层结构？**
JDK 8：数组 + 链表 + 红黑树。容量永远是 2 的幂（为了用 `(n-1) & hash` 代替取模）；负载因子 0.75；链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树。

**Q7. `ArrayList` 和 `LinkedList` 的区别？**
`ArrayList` 底层数组，随机访问 O(1)，中间插入删除 O(n)；`LinkedList` 底层双向链表，插入删除 O(1)，随机访问 O(n)。**实际开发 99% 用 `ArrayList`。**

**Q8. 受检异常和运行时异常的区别？**
受检异常编译器强制处理（`IOException`、`SQLException`），代表外部环境问题；运行时异常不强制（`NullPointerException`），代表代码 bug。

### MySQL

**Q9. 为什么用 `DECIMAL` 存钱？**
`FLOAT`/`DOUBLE` 是二进制浮点数，无法精确表示 0.1 这类十进制小数，累加会产生误差。`DECIMAL` 是定点数，精确。

**Q10. `utf8` 和 `utf8mb4` 的区别？**
MySQL 的 `utf8` 最多 3 字节，存不了 emoji 和部分生僻字；`utf8mb4` 才是完整的 4 字节 UTF-8。**一律用 `utf8mb4`。**

**Q11. `COUNT(*)` 和 `COUNT(列)` 的区别？**
`COUNT(*)` 数行，`COUNT(列)` 数非 NULL 值。LEFT JOIN 后统计右表条数必须用 `COUNT(右表主键)`。

**Q12. SQL 的执行顺序？**
`FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`。这解释了为什么 `WHERE` 不能用 `SELECT` 的别名、不能用聚合函数。

**Q13. 索引为什么能加速？**
索引把列值排序后单独存储，因为有序才能二分查找，O(n) 变 O(log n)。InnoDB 用 B+ 树，非叶子只存键、叶子存数据并链表相连，支持范围查询。

**Q14. 什么是回表？什么是覆盖索引？**
二级索引的叶子只存主键值，查完整行要拿主键回主键索引再查一次，叫回表。如果 `SELECT` 的列全在索引里就不用回表，叫覆盖索引。

**Q15. 索引失效的常见情况？**
对列用函数、隐式类型转换、`LIKE '%x'`、`OR` 两边有一边无索引、不满足最左前缀。

**Q16. 索引越多越好吗？**
不是。索引占空间，且每次 `INSERT`/`UPDATE` 都要维护所有索引，拖慢写入。一般一张表 5–6 个是上限。

**Q17. 事务的 ACID？**
原子性（全做或全不做）、一致性（合法状态到合法状态）、隔离性（并发互不干扰）、持久性（提交后不丢）。

**Q18. MySQL 的默认隔离级别？为什么？**
`REPEATABLE READ`。原因：MVCC 让 RR 代价很小；老版本 `STATEMENT` 格式的 binlog 在 RC 下会导致主从不一致；历史惯性。**注意 Oracle/PG 默认是 `READ COMMITTED`。**

**Q19. 脏读、不可重复读、幻读的区别？**
脏读读到未提交数据；不可重复读是同一行在同一事务内两次读不一样；幻读是同一范围的行数变了。前两个针对"行"，第三个针对"行数"。

**Q20. MVCC 是什么？**
多版本并发控制。每行保留多个版本，事务读自己开始时有效的那个版本，**读不加锁、写不阻塞读**。这就是 MySQL 用 RR 还不慢的原因。

**Q21. 持久性是怎么保证的？**
redo log（WAL）。`COMMIT` 返回前把修改写入 redo log 并 fsync，数据页可以之后慢慢刷盘。断电后重启重放日志恢复。

**Q22. 什么是长事务？有什么危害？**
开了很久没提交的事务。它一直持锁，会阻塞其他事务；还会让 undo log 无法清理。排查用 `information_schema.INNODB_TRX`。

### JDBC

**Q23. JDBC 是什么？**
Java 访问数据库的标准规范，由各数据库厂商提供驱动实现。

**Q24. JDBC 的步骤？**
加载驱动（4.0 后可省）→ 获取连接 → 创建语句 → 执行 → 处理结果 → 关闭资源。

**Q25. `Statement` 和 `PreparedStatement` 的区别？**
`PreparedStatement` 预编译、参数化，能防 SQL 注入，还能复用执行计划；`Statement` 是字符串拼接，有注入风险。

**Q26. `PreparedStatement` 为什么能防注入？**
它先把 SQL 模板发给数据库解析、固定结构，再把参数值单独发送。**值永远不会被当成语法解析。**

**Q27. `PreparedStatement` 能防所有注入吗？**
不能。表名、列名、`ORDER BY` 字段这些"标识符"位置不能用 `?`，必须自己做白名单校验。

**Q28. JDBC 怎么管理事务？**
`conn.setAutoCommit(false)` → 执行多条 SQL → 全部成功 `commit()`，任何异常 `rollback()`。

### 泛型与反射

**Q29. 什么是类型擦除？**
编译器生成字节码前，把 `<T>` 换成它的上界（默认 `Object`），并在所有 `get()` 调用点自动插强转。所以 `Box<Book>` 和 `Box<String>` 运行期是同一个类，`getClass()` 相等。

**Q30. Java 的泛型是"伪泛型"吗？**
是——但这说的不是"写得对不对"，是**和 C# 的对比**：Java 用**类型擦除**，编译后 `T` 变成 `Object` 或上界；C# 的 CLR **在运行时保留类型参数**。
Java 的代价是运行时拿不到类型信息（不能 `new T()`、不能 `instanceof T`、`List<String>` 和 `List<Integer>` 是同一个类）；好处是编译期照样全拦（塞个 `String` 进 `Box<Book>` 直接编译报错）。
另：如果看到"形参没被使用"的写法（声明 `<T>` 但字段全用 `Object`），那叫**空泛型壳子**，不叫"假泛型"。

**Q31. 注解的 Retention 有哪三种？默认是哪个？**
`SOURCE`（编译后丢弃）、`CLASS`（class 文件里有，JVM 加载时丢弃）、`RUNTIME`（运行期保留）。**默认是 `CLASS`** —— 所以想用反射读，必须显式写 `@Retention(RUNTIME)`，否则静默失效。

**Q32. 反射能突破 private 吗？能破坏单例吗？**
能。`setAccessible(true)` 之后可以读写私有字段、调用私有构造器。
所以**普通类和静态内部类单例都能被反射破坏**；**枚举挡得住**（`IllegalArgumentException: Cannot reflectively create enum objects`）。

### 并发

**Q33. `count++` 为什么线程不安全？**
它是三步：读 → 加 → 写。两个线程可能同时读到旧值，各自加 1 后写回，**结果只加了 1**。
三种修法：`synchronized`、`AtomicInteger`、`LongAdder`（高并发计数场景）。

**Q34. `volatile` 能保证原子性吗？**
**不能。** 它只保证可见性和有序性。
`volatile int count; count++` 仍然会丢数据 —— 实测丢 6000–1 万。要原子性必须用 `AtomicInteger` 或加锁。

**Q35. `volatile` 的两个作用？**
① 保证可见性：每次读都去主内存读，不缓存副本；② 禁止指令重排。

**Q36. `synchronized` 锁的是什么？**
`void m()` 锁 `this`（每个实例一把）；`static void m()` 锁 `Xxx.class`（全 JVM 一把）；`synchronized(obj)` 锁 obj。
**锁必须锁在"被保护的那份数据"上** —— 数据是 static 的，锁就必须是 static 的。

**Q37. `synchronized` 和 `volatile` 的区别？**
`volatile` 轻量、不阻塞、只保可见性和有序性；`synchronized` 重量、会阻塞、原子性/可见性/有序性都保。
`volatile` 的可见性是**谁都能看到最新值**；`synchronized` 的可见性**只在进同一把锁的线程之间生效**。

**Q38. 双重检查单例为什么必须加 `volatile`？**
`instance = new X()` 是三步：分配内存 → 调用构造器初始化 → 赋引用。**2 和 3 可能被重排**，别的线程可能拿到"引用有值、字段还是默认值"的半成品。`volatile` 禁止这次重排。

**Q39. 静态内部类单例为什么线程安全？**
JVM 保证一个类只被初始化一次（`<clinit>`），且类加载过程本身加锁。而且它是**延迟加载**的：不调用 `getInstance()`，内部类根本不会被加载。

**Q40. 线程池的七个参数？**
`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`。

**Q41. 任务提交进线程池后的流程？**
① 线程数 < core → 建核心线程直接跑；② 队列没满 → 进队列；③ 线程数 < max → 建非核心线程直接跑；④ 都满 → 拒绝策略。
**入队在扩容之前** —— 所以队列无界时，第 ③ 步永远走不到，`maximumPoolSize` 形同虚设。

**Q42. 四种拒绝策略？生产环境用哪个？**
`AbortPolicy`（抛异常，**最诚实**）、`CallerRunsPolicy`（提交者自己跑，一个不丢但拖住调用方）、`DiscardPolicy`（静默丢新的）、`DiscardOldestPolicy`（丢最老的，会打乱顺序）。
生产环境通常用 `AbortPolicy` 或自定义（**记录被拒任务，再决定重试还是报错**）。**`Discard` 系只在"丢了也无所谓"的场景用。**

**Q43. 为什么阿里规约禁止 `Executors`？**
`newFixedThreadPool` 用 `LinkedBlockingQueue`（容量 `Integer.MAX_VALUE`）→ 队列永不满 → 任务无限堆积 → OOM。
`newCachedThreadPool` 的 `maximumPoolSize = Integer.MAX_VALUE` → 线程无限增长。
**必须自己 `new ThreadPoolExecutor(...)`，七个参数写清楚。**

### 工程细节

**Q44. 为什么金额必须用 `BigDecimal`？**
`double` 是二进制浮点，表示不了 0.1；`int` 会截断小数位。`BigDecimal` 是十进制精确表示。
注意：不能 `==` / `+ - * /`，必须 `compareTo` / `add` / `subtract` / `multiply` / `divide`；构造用**字符串**不用 `double`；`equals` 连 scale 一起比，比数值用 `compareTo`。

**Q45. 为什么用 `getGeneratedKeys()` 而不是 `SELECT MAX(id)`？**
并发下会拿到别人的 id（A 插入得 11、B 插入得 12、A 查 `MAX` 拿到 12）；而且事务回滚后自增 id 已消耗，`MAX` 和实际分配对不上。
`getGeneratedKeys()` 底层是 `LAST_INSERT_ID()`，**连接级**的，每个连接各记各的，并发安全。

**Q46. 为什么 name 不能当主键/删除条件？**
`name` 是**属性**（会变、会重复），`id` 才是**身份**（永不变、唯一）。
`DELETE WHERE name = ?` 会删掉所有同名的记录 —— 想删的是"第 11 本"，删掉的是"所有叫围城的"。

## 这份手册的写法约定

往后每次更新，遵守三条：

1. **只写亲手跑过的** —— 每个数字都能对上某一次运行的输出
2. **带具体数值** —— 不写"会丢数据"，写"丢 3–6 万"；不写"很慢"，写"132ms vs 4ms"
3. **写清"我当时以为"** —— 错判本身也是知识（比如"以为 `synchronized` 加了就安全"）
