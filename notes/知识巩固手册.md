# 一、Java 语言核心

## 1.1 类与对象

**一句话**：类是一张图纸，对象是按图纸造出来的房子。

```java
public class Book {
    private String name;      // 字段：每个对象各有一份
    private int price;

    public Book(String name, int price) {   // 构造器：造对象时自动执行
        this.name = name;
        this.price = price;
    }

    public void print() {      // 方法：对象能做什么
        System.out.println(name + ", " + price + "元");
    }
}
```

### 必须记住的四件事

**① 字段用 `private`，通过方法访问（封装）**

不是"习惯问题"，是**不变量保护**。字段公开，外面就能随便改，你的校验形同虚设。

**② 构造器的名字必须和类名一样，没有返回类型**

写 `public void Book(...)` 不是构造器，是一个普通方法 —— **编译通过，但 `new Book()` 永远调不到它。**

**③ `this` 指的是"当前这个对象"**

只有参数名和字段名冲突时才必须写 `this.name = name`。不冲突时可以不写。

**④ 类名首字母大写**

`Book` 不是 `book`。Java 的命名约定，不是语法强制，但**全行业都这么写，不这么写会被认为不专业**。

### 不变量与 setter

> **不变量（invariant）= 这个对象在任何时刻都必须成立的条件。**

| 类 | 不变量 | setter 策略 |
|---|---|---|
| `Circle` | `r > 0`（单字段） | 可以有 `setR()`，里面做校验 |
| `Triangle` | `a + b > c`（**多字段联动**） | **不能**有独立的 `setA()`，因为单改一个会破坏不变量 |

**多字段共享一个不变量时，只能整体替换，不能单独改一个。**

## 1.2 继承与多态

```java
public class EBook extends Book {
    private int fileSize;

    public EBook(String name, int price, int fileSize) {
        super(name, price);      // ← 必须是构造器第一行
        this.fileSize = fileSize;
    }

    @Override
    public void print() {        // 重写父类方法
        super.print();
        System.out.println(fileSize + "MB");
    }
}
```

### 多态：Java 最核心的一件事

```java
Book b = new EBook("三体", 23, 5);
b.print();     // 调用的是 EBook 的 print()，不是 Book 的
```

**编译时看左边，运行时看右边。**

- 左边的 `Book` 决定**能调用哪些方法**（编译期检查）
- 右边的 `EBook` 决定**实际执行哪个版本**（运行期动态绑定）

这就是为什么 `ArrayList<Book>` 里能混装 `PaperBook` 和 `EBook`，一个循环全部正确打印。

### 什么时候必须用父类引用

不是所有地方都要。三种典型场景：

1. **集合统一管理**：`List<Book> shelf` 装各种子类
2. **方法参数通用化**：`void printAll(List<Book> books)`
3. **面向接口编程**：`Downloadable d = new EBook(...)`

### 重载 vs 重写

| | 重载 Overload | 重写 Override |
|---|---|---|
| 发生在 | **同一个类**里 | 父子类之间 |
| 方法名 | 相同 | 相同 |
| 参数列表 | **必须不同** | **必须相同** |
| 返回类型 | 无所谓 | 相同或是子类型 |
| 作用 | 同一个动作的不同入参形式 | 子类改变父类的行为 |

```java
void print()          {}
void print(String s)  {}   // 重载：参数不同

@Override
void print()          {}   // 重写：一模一样
```

### 重写的三级限制

1. **访问权限不能变小**：父类 `public`，子类不能写成 `protected`
2. **不能抛更宽的受检异常**
3. **`static` 方法不能被重写**（它属于类，不属于对象）

## 1.3 抽象类 vs 接口

| | 抽象类 `abstract class` | 接口 `interface` |
|---|---|---|
| 关键字 | `extends`（单继承） | `implements`（可多实现） |
| 能有构造器吗 | **能**（但不能直接 `new`） | 不能 |
| 能有字段吗 | 能，任意类型 | 只能是 `public static final` 常量 |
| 能有方法体吗 | 能，普通方法 | Java 8 起可以用 `default` |
| 表达什么 | **"是什么"**（is-a） | **"能做什么"**（can-do） |
| 什么时候用 | 有共享的字段和实现 | 只需要约定一组能力 |

```java
public abstract class Book {          // 抽象类：书都有名字和价格
    protected String name;
    public abstract String getType(); // 抽象方法：子类必须实现
}

public interface Downloadable {       // 接口：能下载
    void download();                  // 默认就是 public abstract
}
```

### 三个必踩的坑

**① 抽象类不能实例化**

```
java: Book is abstract; cannot be instantiated
```

正确理解：不是"不能用"，是"**没资格直接用**"。它的子类可以。

**② 接口方法默认 `public`，实现时必须写 `public`**

```java
@Override
void download() { }          // ✗ 编译错误：正在尝试分配更低的访问权限

@Override
public void download() { }   // ✓
```

**③ 漏写 `implements` 时，`@Override` 会报错**

```
java: 方法未从其超类重写方法
```

因为编译器找不到父类上有这个方法。**看到这个错误，先检查 `implements` 写了没。**

## 1.4 异常

```
Throwable
├── Error                  ← 程序无法处理（OutOfMemoryError）
└── Exception
    ├── 受检异常 Checked    ← 编译器强制你处理（IOException）
    └── RuntimeException    ← 非受检，运行时才炸（NullPointerException）
```

### 核心区别

| | 受检异常 | 运行时异常 |
|---|---|---|
| 必须 `try-catch` 或 `throws` 吗 | **必须** | 不强制 |
| 代表什么 | 外部环境问题（文件不存在、网络断） | 代码 bug（空指针、数组越界） |
| 例子 | `IOException`、`SQLException` | `NullPointerException`、`NumberFormatException` |

### 自定义业务异常

```java
public class BookException extends RuntimeException {
    public BookException(String message) {
        super(message);
    }
}
```

**为什么继承 `RuntimeException` 而不是 `Exception`？**

因为业务校验失败（价格不能为负）属于**调用方用错了**，不是环境问题。继承 `RuntimeException` 就不用每次都在方法签名上写 `throws`，调用方的负担小。

### try-catch-finally 的执行顺序

```java
try {
    return 1;
} finally {
    System.out.println("一定会执行");
}
```

`finally` **一定会执行**，即使 `try` 里有 `return`。执行顺序是：算好返回值 → 执行 `finally` → 真正返回。

> **注意 `finally` 里有 `return` 会覆盖 `try` 的返回值** —— 这是经典面试坑，也是实际项目里绝对不该写的代码。

### 三个容易混的词

- `final` —— 修饰符，表示"不能改"（变量、方法、类）
- `finally` —— 代码块，表示"一定执行"
- `finalize()` —— 方法，GC 前调用（**已废弃，不要用**）

## 1.5 集合

### ArrayList

```java
ArrayList<Book> shelf = new ArrayList<>();
shelf.add(new Book("活着", 45));
shelf.get(0);
shelf.remove(0);        // 按下标删
shelf.size();
for (Book b : shelf) { } // 增强 for
```

**底层是数组。** 默认容量 10，满了扩容到 **1.5 倍**。

**优点**：随机访问 O(1)（`get(i)` 直接算地址）
**缺点**：中间插入/删除 O(n)（要把后面所有元素往前挪）

### 经典坑：`remove(int)` vs `remove(Object)`

```java
ArrayList<Integer> list = new ArrayList<>(List.of(1, 2, 3));
list.remove(1);              // 删除【下标 1】，即元素 2
list.remove(Integer.valueOf(1));  // 删除【元素 1】
```

**为什么？** 因为 `remove(int index)` 和 `remove(Object o)` 是重载。传 `int` 走下标版本，传对象走元素版本。

### HashMap

```java
HashMap<String, Book> shelf = new HashMap<>();
shelf.put("活着", new Book(...));
shelf.get("活着");            // O(1)
shelf.containsKey("活着");
shelf.remove("活着");         // 只能按 key 删
for (String key : shelf.keySet()) { }
```

**底层（JDK 8）**：数组 + 链表 + 红黑树

```
hash(key) → (n-1) & hash → 数组下标
                            ↓
                     同一格子里的元素用链表串起来
                            ↓
                     链表长度 ≥ 8 且数组长度 ≥ 64 时，转红黑树
```

**四个关键数字**：

| 参数 | 值 | 含义 |
|---|---|---|
| 默认容量 | 16 | 数组长度，**永远是 2 的幂** |
| 负载因子 | 0.75 | 元素数 / 容量超过它就扩容 |
| 扩容 | 2 倍 | 容量翻倍，所有元素重新分布 |
| 树化阈值 | 8 | 链表长度达到 8 转红黑树 |

**为什么容量必须是 2 的幂？**

因为 `(n-1) & hash` 只有在 n 是 2 的幂时，才等价于 `hash % n`，而且位运算比取模快得多。

**为什么要 `h ^ (h >>> 16)`？**

让高位也参与运算。否则 `hash` 的高 16 位在 `& (n-1)` 时全被丢掉，低位相同的 key 会挤在一起。

### equals 与 hashCode 的契约

> **重写 `equals` 必须同时重写 `hashCode`。**

- 两个对象 `equals` 相等 → `hashCode` **必须**相等
- `hashCode` 相等 → `equals` **不一定**相等（哈希冲突）

**反例（只写 equals 不写 hashCode）**：两个 `equals` 相等的对象哈希值不同 → 被放进不同的格子 → `HashMap.get()` 找不到它。

**反例（只写 hashCode 不写 equals）**：哈希值相同但 `equals` 是引用比较 → 同一个格子里判定为不同对象 → 也找不到。

### `==` vs `equals`

```java
String a = new String("abc");
String b = new String("abc");
a == b        // false（比较引用地址）
a.equals(b)   // true（比较内容）

Integer x = 127, y = 127;
x == y        // true（Integer 缓存 -128~127）
Integer m = 128, n = 128;
m == n        // false（超出缓存，是两个对象）
```

**结论：比较内容永远用 `equals`，`==` 只用于基本类型和判 null。**

## 1.6 文件 IO

```java
// 读
List<String> lines = Files.readAllLines(Path.of("shelf.txt"));

// 写
Files.write(Path.of("shelf.txt"), lines);
```

比老的 `FileReader`/`BufferedReader` 简洁得多。**新的项目优先用 `java.nio.file`。**

### try-with-resources

```java
try (BufferedReader br = Files.newBufferedReader(path)) {
    ...
}   // 自动 close，即使抛异常
```

括号里声明的资源，离开 `try` 块时会**自动关闭**，关闭顺序与声明顺序**相反**。

**为什么重要**：不关闭 → 文件句柄泄漏 → 最终 `Too many open files`。

# 二、MySQL 数据库

## 2.1 建表与约束

```sql
CREATE TABLE book (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(100) NOT NULL,
    type        VARCHAR(10)  NOT NULL DEFAULT 'PAPER',
    price       DECIMAL(8,2) NOT NULL CHECK (price >= 0),
    pages       INT          NOT NULL CHECK (pages > 0),
    file_size   INT          NULL,          -- 只有电子书有，所以允许 NULL
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 字段类型选择

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 主键 | `BIGINT AUTO_INCREMENT` | 自增保证插入总在末尾，不用挪数据 |
| **钱** | `DECIMAL(10,2)` | **绝不能用 `FLOAT`/`DOUBLE`**，浮点数算不准 0.1+0.2 |
| 短文本 | `VARCHAR(n)` | n 按实际需要，别一律 `VARCHAR(255)` |
| 大文本 | `TEXT` | 不占行内空间 |
| 时间 | `DATETIME` | 与时区无关；`TIMESTAMP` 会随时区转换 |
| 布尔 | `TINYINT(1)` | MySQL 没有真正的 BOOLEAN |

**`DECIMAL(8,2)` 的含义**：总共 8 位数字，其中 2 位是小数。所以整数部分最多 6 位，最大 999999.99。

### 字符集：utf8 vs utf8mb4

**MySQL 的 `utf8` 是残废的**，最多 3 字节，存不了 emoji 和部分生僻字。
**`utf8mb4` 才是完整的 UTF-8**（4 字节）。

> **建库建表一律 `utf8mb4`。** 看到 `utf8` 就当它是历史遗留。

### 三大范式（人话版）

| 范式 | 人话 | 违反的后果 |
|---|---|---|
| 1NF | 一个格子里只能有一个值 | `authors = "刘慈欣,李淼"` 无法按作者查询 |
| 2NF | 非主键列必须依赖**整个**主键 | 联合主键 `(book_id, author_id)` 里存书名，书名只依赖 book_id |
| 3NF | 非主键列不能依赖另一个非主键列 | 存了 `出版社id` 又存 `出版社名`，改名要改几千行 |

**判断要不要拆表的正确问法**（不是"空列够多就拆"）：

> **这一列是"所有书都有的"，还是"某一类书才有的"？**

- 出版社、出版年份 —— 所有书都有 → `book` 表，`NOT NULL`
- `file_size` —— 只有电子书有 → 允许 `NULL`（或者拆子表）

### 多对多的正确建法

❌ **错误**：`book` 表加一列 `authors VARCHAR`，存 `"刘慈欣,李淼"`

三个问题：
1. 一格多值，违反 1NF
2. 没法用 SQL 查"刘慈欣写过哪些书"
3. 作者改名要改所有书

✅ **正确**：三张表

```sql
author(id, name)
book(id, name, price, ...)
book_author(book_id, author_id,
            PRIMARY KEY (book_id, author_id),
            FOREIGN KEY (book_id)   REFERENCES book(id),
            FOREIGN KEY (author_id) REFERENCES author(id))
```

**联合主键 `(book_id, author_id)` 天然去重**，同一个人同一本书插两次直接报：

```
ERROR 1062: Duplicate entry '2-1' for key 'book_author.PRIMARY'
```

## 2.2 查询

### JOIN 的四种

| 类型 | 语义 | 结果 |
|---|---|---|
| `INNER JOIN` | 两边都有才留 | 只留匹配上的 |
| `LEFT JOIN` | **左表全留**，右表没有就 NULL | 至少和左表一样多 |
| `RIGHT JOIN` | 右表全留 | 实际很少用，改成 LEFT 换位置 |
| 反连接 | `LEFT JOIN ... WHERE 右表主键 IS NULL` | 找出"没有关联"的行 |

```sql
-- 所有书 + 作者名（没有作者的书也要出现）
SELECT b.name, b.price, a.name AS author
FROM book b
LEFT JOIN book_author ba ON b.id = ba.book_id
LEFT JOIN author a       ON ba.author_id = a.id;
```

**`LEFT JOIN` 的 `WHERE` 里加右表条件会退化成 `INNER JOIN`**：

```sql
-- ✗ 写法错误：NULL 行被过滤掉了
LEFT JOIN author a ON ... WHERE a.name = '刘慈欣'

-- ✓ 条件要放 ON 里
LEFT JOIN author a ON ... AND a.name = '刘慈欣'
```

### 聚合与执行顺序

```sql
SELECT type, COUNT(*) AS 本数, AVG(price) AS 均价
FROM book
WHERE price > 10
GROUP BY type
HAVING COUNT(*) >= 2
ORDER BY 均价 DESC
LIMIT 1;
```

**执行顺序（必须背下来）**：

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

这个顺序解释了两个现象：

1. **`WHERE` 里不能用 `SELECT` 起的别名**（那时还没算出来），但 `ORDER BY` 可以
2. **`WHERE` 里不能用聚合函数**（分组还没发生），要用 `HAVING`

```
ERROR 1111: Invalid use of group function
```

### `COUNT(*)` vs `COUNT(列)`

```sql
-- 没写过书的作者，COUNT(*) 会算成 1
SELECT a.name, COUNT(*)            FROM author a LEFT JOIN book_author ba ON ... GROUP BY a.id;  -- 鲁迅 → 1 ✗
SELECT a.name, COUNT(ba.book_id)   FROM author a LEFT JOIN book_author ba ON ... GROUP BY a.id;  -- 鲁迅 → 0 ✓
```

**原理**：`COUNT(*)` 数**行**，`COUNT(列)` 数**非 NULL 值**。LEFT JOIN 没匹配到的时候，右表所有列都是 NULL。

**规则：LEFT JOIN 之后统计"右表有几条"，必须用 `COUNT(右表主键)`。**

### NULL 的坑

```sql
SELECT * FROM book WHERE file_size = NULL;    -- ✗ 永远 0 行
SELECT * FROM book WHERE file_size IS NULL;   -- ✓
```

因为 `NULL = NULL` 的结果是 `UNKNOWN`，不是 `TRUE`。**NULL 只能用 `IS NULL` / `IS NOT NULL`。**

同样的道理：`SUM` / `AVG` 会**跳过 NULL**，所以 `AVG(price)` 的分母是"非 NULL 的行数"，不是总行数。

## 2.3 索引

### 为什么快

> **索引就是把某一列排序后单独存一份，并记住每个值对应的行在哪。**
> **因为有序，才能二分。O(n) → O(log n)。**

InnoDB 用 **B+ 树**，三个关键特性：

| 特性 | 后果 |
|---|---|
| 只有叶子存数据，非叶子只存键 | 三层就能存千万级，一次查询 3 次磁盘读 |
| 叶子之间用链表相连 | 范围查询可以顺着链表扫 |
| 主键索引的叶子就是整行（聚簇索引） | 所以主键最好自增，插入总在末尾 |

### 回表与覆盖索引

```sql
SELECT * FROM book WHERE name = '活着';
```

两步：
1. 在 `name` 索引里找到 → 得到主键 `id = 1`
2. 拿 `id` **回到主键索引**取整行 ← **这叫回表**

```sql
SELECT id FROM book WHERE name = '活着';   -- 快：索引里就有 id，不回表
SELECT * FROM book WHERE name = '活着';    -- 慢：要回表
```

**如果 `SELECT` 要的列全在索引里，就不用回表，这叫「覆盖索引」。** 面试答"怎么优化这个查询"，答这个就是加分项。

### 索引失效的五种写法

| 写法 | 为什么失效 | 怎么改 |
|---|---|---|
| `WHERE YEAR(created_at) = 2026` | 对列用了函数 | `created_at >= '2026-01-01' AND < '2027-01-01'` |
| `WHERE name = 123`（name 是 VARCHAR） | **隐式类型转换** | `WHERE name = '123'` |
| `WHERE name LIKE '%活着'` | 前面有 `%` 无法二分 | 只有 `LIKE '活着%'` 能用 |
| `WHERE a = 1 OR b = 2`（b 无索引） | OR 要求两边都有索引 | 给 b 建索引，或拆成两个查询 `UNION` |
| 联合索引 `(a,b,c)` 只查 `b` | 不满足**最左前缀** | 查询条件必须从 `a` 开始 |

**最容易踩的是第二条**：`VARCHAR` 列和数字比较时，MySQL 把列转成数字再比，索引直接报废，**而且不报错**。

### 用 EXPLAIN 验证

```sql
EXPLAIN SELECT * FROM book WHERE price = 45;
```

重点看三列：

| 列 | 关注什么 |
|---|---|
| `type` | `const` > `eq_ref` > `ref` > `range` > **`index` ≈ `ALL`（都要避免）** |
| `key` | 实际用了哪个索引，`NULL` 表示没走索引 |
| `rows` | 预计扫多少行，越小越好 |

**`type: index` 不是"用了索引"**，是"扫描了整个索引树"，跟全表扫差不多。**这条最容易误解。**

### 索引的第二重作用：决定锁多少行 ⭐

> 这一点比"查询变快"更重要，是线上事故的高发区。

**实测结论**（3 行小表，会话 1 改 a 行，会话 2 改完全不同的 b 行）：

| 场景 | 结果 | 耗时 |
|---|---|---|
| `name` **无索引** | **ERROR 1205 锁等待超时** | 3.4 秒 |
| `name` **有索引** | 更新成功 | **0.3 秒** |

**原因**：`WHERE` 列没有索引 → 只能全表扫描 → InnoDB 在 RR 下把**扫描到的每一行都锁上**（还有间隙锁）→ **你只想改一行，结果锁了整张表。**

**生产环境的表现**：一句 `UPDATE orders SET status = ... WHERE status = '待处理'`（`status` 没索引），会把整张订单表锁死，所有写操作全部卡住。**这就是"数据库突然全员卡死、重启后又好了"的真凶。**

**结论：给经常出现在 `WHERE` / `JOIN` / `ORDER BY` 的列建索引，不只是为了快，也是为了少锁。**

### 索引的代价

- 占磁盘（等于把那列复制一份）
- **拖慢写入**：`INSERT` 一行，所有索引都要更新
- 拖慢更新：改了被索引的列，索引要重排

**经验值：一张表 5–6 个索引是正常上限。看到 20 个索引，那多半是乱建的。**

## 2.4 事务

### 为什么需要

张三转李四 100 块，两条 SQL：

```sql
UPDATE account SET balance = balance - 100 WHERE name = '张三';
UPDATE account SET balance = balance + 100 WHERE name = '李四';
```

第一条执行完、第二条没执行时断电 → **张三少了 100，李四没收到，钱凭空消失。**

### 三个命令

```sql
START TRANSACTION;   -- 开始打包（也可以写 BEGIN）
  ...SQL...
COMMIT;              -- 确认，全部生效
-- 或
ROLLBACK;            -- 反悔，全部撤销
```

### 最反直觉的现象

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 300 WHERE name = '张三';
SELECT * FROM account;    -- 显示 700（你自己看得见）
ROLLBACK;
SELECT * FROM account;    -- 变回 1000
```

> **事务里做的修改，只有你自己看得见。别人看不见，磁盘上也不算数。直到 COMMIT 才落地。**

### ACID

| 字母 | 英文 | 意思 | 转账场景 |
|---|---|---|---|
| **A** | Atomicity 原子性 | 要么全做，要么全不做 | 不会出现扣了张三、没加李四 |
| **C** | Consistency 一致性 | 数据从一个合法状态到另一个合法状态 | 转账前后总额必须都是 1500 |
| **I** | Isolation 隔离性 | 并发事务互不干扰 | 后一个事务必须等前一个结束 |
| **D** | Durability 持久性 | 提交了就一定不丢 | `COMMIT` 返回后，断电也不丢 |

### ⚠️ 最重要的陷阱：MySQL 只回滚"出错的那一条"

**实测结果**（初始：张三 50，李四 500，总额 550）：

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE name = '张三';  -- ERROR 3819 CHECK 约束失败
UPDATE account SET balance = balance + 100 WHERE name = '李四';  -- Query OK，照常执行
COMMIT;
```

| | 张三 | 李四 | 总额 |
|---|---|---|---|
| 转账前 | 50 | 500 | **550** |
| 转账后 | 50 | **600** | **650** |

**凭空多了 100 块。**

**原因**：MySQL 出错时**只回滚出错的那一条语句**，事务本身还活着，后续语句继续执行，`COMMIT` 把李四那条提交了。

> ⚠️ 注意：**PostgreSQL 不是这样**。PG 一旦出错，整个事务作废，后面语句全报 `current transaction is aborted`。**MySQL 不会 —— 所以这里更容易踩坑。**

**结论**：

> **数据库不知道你这两条 UPDATE 是一件事。"它们必须一起成功"这个判断，只能由写代码的人来做。**

### 正确写法（记住这段模板）

```java
conn.setAutoCommit(false);      // 等于 START TRANSACTION
try {
    // 一堆 SQL
    conn.commit();
} catch (Exception e) {
    conn.rollback();            // 任何一步出错，全部撤销
    throw e;
}
```

### 持久性靠 redo log，不是"数据已写盘"

`COMMIT` 返回的一瞬间，数据页**很可能还在内存里**（buffer pool），没落盘。

```
1. 改内存里的数据页                    ← 快，但断电就没了
2. 把"改了哪行、改成什么"写进 redo log，fsync 到磁盘   ← COMMIT 返回前必须完成
3. 空闲时再把内存页慢慢刷到磁盘
```

断电重启后，MySQL 读 `redo log` **重放**这些操作，数据就回来了。

> **这叫 WAL（Write-Ahead Logging，预写日志）。**
> **COMMIT 返回时，日志已经落盘，但数据本身没有。持久性靠的是日志。**

正因为只需顺序写一条日志（而不是等随机写数据页），MySQL 才能做到每秒几千次提交。

### 事务要短

事务从 `START TRANSACTION` 到 `COMMIT` 之间一直持有锁。**事务里不要等用户输入、不要调外部接口。**

> 真实事故里一大类叫"长事务把数据库拖死"：一个人开了事务忘了提交，几小时后全系统的写操作卡死。

排查工具：

```sql
SELECT trx_id, trx_state, trx_started, trx_isolation_level,
       trx_rows_modified, trx_query
FROM information_schema.INNODB_TRX;
```

**线上"突然变慢、写入全卡"的第一步排查，就是看这里有没有开了几小时的事务。**

## 2.5 隔离级别

### 三种并发问题

| 现象 | 一句话 | 比喻 |
|---|---|---|
| **脏读** dirty read | 读到别人**还没提交**的数据 | 别人改了草稿还没保存，你就照着抄了 |
| **不可重复读** non-repeatable read | 同一事务里读同一行，**两次不一样** | 你抄第一页，他改了第二页，回头对不上 |
| **幻读** phantom read | 同一事务里查同一范围，**行数不一样** | 你数了 5 份文件，他塞进 1 份，你再数是 6 份 |

> **不可重复读改的是同一行；幻读多出来的是新行。** 这是唯一的区别，也是面试最爱考的那一句。

### 四个档位

| 级别 | 脏读 | 不可重复读 | 幻读 | 默认在哪 |
|---|---|---|---|---|
| `READ UNCOMMITTED` | 会 | 会 | 会 | 没人用 |
| `READ COMMITTED` | 不会 | 会 | 会 | Oracle / PostgreSQL |
| `REPEATABLE READ` | 不会 | 不会 | InnoDB 基本不会 | **MySQL** |
| `SERIALIZABLE` | 不会 | 不会 | 不会 | 几乎不用 |

```sql
-- 只影响下一个事务
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
START TRANSACTION;
```

> **`SET TRANSACTION` 必须在 `START TRANSACTION` 之前执行。**

### 实测：三种现象的样子

| 实验 | 看到的现象 |
|---|---|
| 脏读（RU） | 李四 500 → **1500**（对方未提交）→ 对方 ROLLBACK 后回 500 |
| 不可重复读（RC） | 同一事务内 500 → **600** |
| RR 快照 | 同一事务内 700 → **700**，`COMMIT` 之后才是 800 |
| 幻读（RR） | `SELECT COUNT(*)` 两次都是 **2**，但 `UPDATE 王五` 返回 **`Rows matched: 1`** |

**最后一行是幻读最精确的样子**：

```
SELECT COUNT(*) FROM account;                          → 2
UPDATE account SET balance = balance WHERE name = '王五';
→ Query OK, 0 rows affected
  Rows matched: 1   Changed: 0   Warnings: 0
```

**`SELECT` 说 2 行，`UPDATE` 说匹配到 1 行。** 同一条记录，在同一个事务里，"看不见"却"摸得到"。

### MVCC：MySQL 靠"记旧版本"而不是"锁"

```
李四 balance 这一行：
  版本1: 500  ← B 的事务开始时就绑定了这个版本
  版本2: 600  ← A 改出来的
  版本3: 700  ← A 又改了一次
```

B 的 `SELECT` 永远读"我事务开始时有效的那个版本"。

> **妙处在于：读不加锁，写不阻塞读。** A 在改，B 在念旧版本，互不干扰。

`REPEATABLE READ` 靠"记住旧版本"，不是靠"锁住"。

### 幻读为什么"基本"解决了

InnoDB 在 RR 下给 `UPDATE ... WHERE 范围` 加了**间隙锁（Gap Lock）**：不只锁匹配的行，还锁住行与行之间的"缝隙"，让别人插不进来。

而普通 `SELECT`（快照读）看不到新插入的行，所以幻读在 MySQL 的 RR 下**大部分场景**被堵住了 —— 但**快照读看不见、当前读（UPDATE/DELETE）看得见**，这就是上表最后一行那个 `2` 和 `1` 的矛盾。

### 为什么 MySQL 默认 RR

1. **MVCC 让 RR 的代价很小**：读不加锁，隔离性提升不额外变慢
2. **主从复制**：老版本 `binlog` 用 `STATEMENT` 格式时，`READ COMMITTED` 会导致主从不一致
3. **历史惯性**

**反面**：用 Seata 这类分布式事务框架时，很多要求 `READ COMMITTED`（需要在事务里看到最新已提交数据），**得手动改。**

# 三、JDBC

## 3.1 JDBC 是什么

> **JDBC 是 Java 官方定的一套"访问数据库"的接口。各数据库厂商（MySQL / Oracle / PostgreSQL）自己提供实现 —— 就是那个驱动 jar。**

好处：`Connection`、`Statement`、`ResultSet` 这些名字**全行业统一**，换数据库只改 URL 和 jar。

**面试标准答案**："Java 访问数据库的标准规范，由各数据库厂商提供驱动实现。"

## 3.2 五个步骤

| 步骤 | 代码 | 说明 |
|---|---|---|
| 1 拿连接 | `DriverManager.getConnection(url, user, pwd)` | url 里写清楚连哪个库 |
| 2 造语句 | `conn.prepareStatement(sql)` | 几乎永远用这个，不用 `createStatement` |
| 3 执行 | `ps.executeQuery()` / `ps.executeUpdate()` | 查 vs 增删改 |
| 4 取数据 | `while (rs.next()) { rs.getString("name") }` | 游标一开始在**第一行之前** |
| 5 关闭 | try-with-resources 自动 | 顺序与打开相反 |

**第 4 步是新手最常错的**：`ResultSet` 不是"装着数据的列表"，是**一根光标**。必须调 `next()` 才能移到第一行。

## 3.3 URL 拆解

```
jdbc:mysql://localhost:3306/bookshelf?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=utf8
└┬─┘└─┬─┘  └───┬───┘└┬─┘└───┬────┘└──────────────────────┬───────────────────────────────────────────┘
 │    │        │     │      │                          └─ 参数（用 & 分隔）
 │    │        │     │      └─ 数据库名
 │    │        │     └─ 端口
 │    │        └─ 主机
 │    └─ 子协议（哪个厂商）
 └─ 协议永远是 jdbc
```

| 参数 | 不写会怎样 |
|---|---|
| `useSSL=false` | 8.0 会刷一堆警告 |
| `serverTimezone` | **时间类型差 8 小时** |
| `characterEncoding=utf8` | 中文可能乱码 |

## 3.4 驱动加载

```java
Class.forName("com.mysql.cj.jdbc.Driver");   // 老写法，现在可以省
```

**JDBC 4.0（Java 6）以后不需要了** —— 驱动 jar 里有 SPI 配置文件，`DriverManager` 会自动找到。

**面试完整答案**：JDBC 4.0 之前必须 `Class.forName` 显式加载；之后靠 SPI 自动加载，可以不写。

## 3.5 SQL 注入 ⭐

### 漏洞代码

```java
String sql = "SELECT id, name, price FROM book WHERE name = '" + input + "'";
```

用户输入 `' OR '1'='1`，拼出来：

```sql
SELECT id, name, price FROM book WHERE name = '' OR '1'='1';
```

**实测结果：整张表 4 行全部返回。**

### 数引号就明白了

```
name = ''  OR  '1'='1'
        ↑↑
        用户输入的第一个引号把字符串提前关掉了
```

- `name = ''` → 找名字为空的书 → 没有
- `OR '1'='1'` → **永远为真**

> **SQL 注入的本质：你以为是"用户输入了一个值"，数据库却以为"用户输入了一段逻辑"。**
> **数据变成了代码。**

### 更狠的：UNION 读别的表

```sql
-- 攻击者输入：' UNION SELECT id, name, balance FROM account --
SELECT id, name, price FROM book WHERE name = '' UNION SELECT id, name, balance FROM account;
```

**实测结果**：返回的是 `account` 表的 3 行（张三 / 李四 / 王五），`balance` 被硬塞进了 `price` 列。

**你想查一本书，结果把别人账户余额查出来了。**

### 登录绕过（最经典）

```java
"SELECT * FROM user WHERE username = '" + name + "' AND password = '" + pwd + "'"
```

用户名输入 `' OR '1'='1' --`：

```sql
SELECT * FROM user WHERE username = '' OR '1'='1' --' AND password = '...'
```

`--` 是 SQL 注释符，**后半段密码校验被整行注释掉了**。查询恒真 → 登录成功。

### 防御：PreparedStatement

```java
String sql = "SELECT id, name, price FROM book WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, input);      // 无论输入什么，都只是"一个值"
ResultSet rs = ps.executeQuery();
```

**同样的注入串，这次返回 `共 0 行`** —— 它只是一个查不到的书名。

### 为什么安全：结构先定死

```
Statement：
  拼出一整条字符串 → 发给 MySQL → MySQL 当成语法解析  ← 危险在这里

PreparedStatement：
  1. 先发模板 "WHERE name = ?"
  2. MySQL 解析它，生成执行计划，结构固定
  3. 再把参数值单独发过去
  4. MySQL 把值填进洞里 —— 它永远只是【值】
```

> **PreparedStatement 的本质不是"把危险字符转义掉"，而是根本不给你"把数据变成语法"的机会。**

### 三个坑

**① `?` 下标从 1 开始**

```java
ps.setString(1, input);   // 第一个问号
```

报错 `Parameter index out of range (0 < 1)` 就是这个。

**② `?` 只能替换值，不能替换表名/列名/ORDER BY 字段**

```java
"SELECT * FROM ? WHERE ? = ?"     // ✗ 语法错误
"ORDER BY ?"                      // ✗ 没用
```

**表名列名属于"结构"，发送模板时就必须确定。** 排序字段必须走白名单：

```java
String column = switch (input) {
    case "price" -> "price";
    case "pages" -> "pages";
    default -> "id";
};
```

> **面试追问："PreparedStatement 能防所有注入吗？"**
> **答：不能。表名、列名、ORDER BY 这些标识符位置它管不到，必须自己做白名单校验。**

**③ `executeQuery` vs `executeUpdate`**

```java
ResultSet rs = ps.executeQuery();    // 查，返回结果集
int rows = ps.executeUpdate();       // 增删改，返回影响行数
```

用错不报错，只是拿到一个没用的对象。

# 四、对比表总汇

| 对比项 | A | B |
|---|---|---|
| `==` | 比较引用/值 | `equals` 比较内容 |
| 重载 | 同类内，参数不同 | 重写：父子类，签名相同 |
| 抽象类 | `extends` 单继承，可有字段和实现 | 接口：`implements` 多实现，只能有常量 |
| `ArrayList` | 数组，随机访问 O(1)，插入删除 O(n) | `LinkedList`：链表，插入 O(1)，随机访问 O(n) |
| `ArrayList.remove(1)` | 删下标 1 | `remove(Integer.valueOf(1))` 删元素 1 |
| `COUNT(*)` | 数行 | `COUNT(列)` 数非 NULL 值 |
| `WHERE` | 分组前过滤，不能聚合 | `HAVING`：分组后过滤，可以聚合 |
| `INNER JOIN` | 只留匹配的 | `LEFT JOIN`：左表全留 |
| 聚簇索引 | 主键索引，叶子是整行 | 二级索引：叶子是主键值，要回表 |
| `type: ref` | 走索引，好 | `type: ALL/index`：全扫，要优化 |
| `READ COMMITTED` | Oracle / PG 默认 | `REPEATABLE READ`：MySQL 默认 |
| `COMMIT` | 日志落盘，数据未必 | `ROLLBACK`：全部撤销 |
| `Statement` | 字符串拼接，可注入 | `PreparedStatement`：参数化，安全 |
| `executeQuery` | 返回 `ResultSet` | `executeUpdate`：返回 `int` |

# 五、常见错误码

| 错误码 | 含义 | 常见原因 |
|---|---|---|
| **1045** | Access denied | 密码错 / 用户无权限 |
| **1048** | Column cannot be null | 插了 NULL 到 NOT NULL 列 |
| **1054** | Unknown column | 列名拼错 / 别名用错（如 `a.name` 但没定义 a） |
| **1062** | Duplicate entry | 主键/唯一索引冲突 |
| **1064** | SQL syntax error | 少逗号 / 少 `ON` / 多条语句混在一起 |
| **1111** | Invalid use of group function | 在 `WHERE` 里用了聚合函数，应该用 `HAVING` |
| **1146** | Table doesn't exist | 表名拼错 / 没 `USE 库名` |
| **1205** | Lock wait timeout exceeded | 别的事务长时间持锁；或 UPDATE 没走索引锁了全表 |
| **1213** | Deadlock found | 两个事务互相等对方的锁 |
| **3819** | Check constraint violated | 违反 `CHECK` 约束（如价格为负） |

**遇到错误的第一反应**：**先读完整报错，不要猜。** 报错里几乎总是写清楚了表名、列名、行号。

| 用 GitHub 网页编辑 | `git push` 被拒（`fetch first`） | **不要用网页编辑，会与本地历史分叉**（犯过 3 次） |
| IDEA 里改了代码，git 说没变化 | `nothing to commit, working tree clean` | IDEA 项目目录和 git 仓库目录**不是同一个** |
| `>` 导出 SQL | PowerShell 默认写 UTF-16 LE（`FF FE`），mysql 读不进 | 用 `\| Out-File -Encoding utf8` 或 `mysqldump --result-file=` |
| 在 mysql 客户端里跑 `mysqldump` | `Unknown command '\U'` | `mysqldump` 是**独立的命令行工具**，不是 SQL |

## 6.3 MySQL 阶段

| 坑 | 现象 | 教训 |
|---|---|---|
| 把报错文本当命令粘回去 | `ERROR 1064` + `->` 续行状态 | 卡在 `->` 时按 `\c` 取消 |
| `SELECT a.name COUNT(...)` | 1064 | 两列之间**少逗号** |
| `LEFT JOIN ba a.id = ba.author_id` | 1064 | **少 `ON`** |
| 自己发明了 `price` 表 | `Table 'bookshelf.price' doesn't exist` | 先确认表名 |
| 用 `bookname` 当关联键 | 作者改名后关联失效 | **用自增 id 当外键** |
| 忘了插"鲁迅" | 聚合结果少一行，坑没踩到 | 实验的数据必须齐 |
| `HAVING COUNT(*) > 2` | `Empty set` | 中文"2 本以上"**包含 2**，要 `>=` |
| `SELECT` 用 `COUNT(列)`、`HAVING` 用 `COUNT(*)` | 数据一变就自相矛盾 | **两处必须用同一个表达式** |
| `LEFT JOIN` 的 `WHERE` 加右表条件 | 退化成 INNER JOIN | 条件放 `ON` 里 |
| 脏读实验"没出现" | 以为隔离级别没生效 | **窗口 A 的 UPDATE 根本没执行**（截图里没有 `Query OK`） |
| `UPDATE` 锁了整张表 | 另一个窗口改**别的行**也报 1205 | **`WHERE` 列没索引 → 全表扫描 → 锁全部行** |

## 6.4 最有价值的三个"意外"

**① 钱凭空多了 100 块**

`START TRANSACTION` 里第一条 UPDATE 报 CHECK 约束失败，第二条照样执行，`COMMIT` 后总额从 550 变 650。

→ **MySQL 只回滚出错的那一条语句，不回滚整个事务。**

**② `SELECT COUNT(*)` 说 2，`UPDATE` 说 `Rows matched: 1`**

幻读最精确的样子：快照读看不见的行，当前读摸得到。

→ **MVCC 给读操作的是"旧版本"，UPDATE 用的是"最新版本"。**

**③ 没索引的 UPDATE 锁了整张表**

改一行，锁全表，另一个窗口改无关的行也超时。

→ **索引不只决定"读多少行"，还决定"锁多少行"。**

# 七、面试问答速查

> 用法：先看问题，**用嘴说出来**，说不出来再看下面的要点。

### Java

**Q1. 面向对象的三大特性？**
封装（隐藏细节，保护不变量）、继承（复用+扩展）、多态（同一接口不同实现）。

**Q2. 重载和重写的区别？**
重载在同一个类里，方法名相同参数不同；重写在父子类之间，签名完全相同。重写有三级限制：权限不能变小、不能抛更宽的受检异常、`static` 不能被重写。

**Q3. 抽象类和接口的区别？**
抽象类表达"是什么"，单继承，可以有字段和构造器；接口表达"能做什么"，多实现，只能有常量。Java 8 后接口可以有 `default` 方法。

**Q4. `==` 和 `equals` 的区别？**
`==` 比较引用地址（基本类型比较值），`equals` 比较内容。比较内容永远用 `equals`。

**Q5. 为什么重写 `equals` 必须重写 `hashCode`？**
契约要求 `equals` 相等的对象 `hashCode` 必须相等。否则在 `HashMap` 里会被放进不同的桶，导致 `get()` 找不到。

**Q6. `HashMap` 的底层结构？**
JDK 8：数组 + 链表 + 红黑树。容量永远是 2 的幂（为了用 `(n-1) & hash` 代替取模）；负载因子 0.75；链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树。

**Q7. `ArrayList` 和 `LinkedList` 的区别？**
`ArrayList` 底层数组，随机访问 O(1)，中间插入删除 O(n)；`LinkedList` 底层双向链表，插入删除 O(1)，随机访问 O(n)。**实际开发 99% 用 `ArrayList`。**

**Q8. 受检异常和运行时异常的区别？**
受检异常编译器强制处理（`IOException`、`SQLException`），代表外部环境问题；运行时异常不强制（`NullPointerException`），代表代码 bug。

### MySQL

**Q9. 为什么用 `DECIMAL` 存钱？**
`FLOAT`/`DOUBLE` 是二进制浮点数，无法精确表示 0.1 这类十进制小数，累加会产生误差。`DECIMAL` 是定点数，精确。

**Q10. `utf8` 和 `utf8mb4` 的区别？**
MySQL 的 `utf8` 最多 3 字节，存不了 emoji 和部分生僻字；`utf8mb4` 才是完整的 4 字节 UTF-8。**一律用 `utf8mb4`。**

**Q11. `COUNT(*)` 和 `COUNT(列)` 的区别？**
`COUNT(*)` 数行，`COUNT(列)` 数非 NULL 值。LEFT JOIN 后统计右表条数必须用 `COUNT(右表主键)`。

**Q12. SQL 的执行顺序？**
`FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`。这解释了为什么 `WHERE` 不能用 `SELECT` 的别名、不能用聚合函数。

**Q13. 索引为什么能加速？**
索引把列值排序后单独存储，因为有序才能二分查找，O(n) 变 O(log n)。InnoDB 用 B+ 树，非叶子只存键、叶子存数据并链表相连，支持范围查询。

**Q14. 什么是回表？什么是覆盖索引？**
二级索引的叶子只存主键值，查完整行要拿主键回主键索引再查一次，叫回表。如果 `SELECT` 的列全在索引里就不用回表，叫覆盖索引。

**Q15. 索引失效的常见情况？**
对列用函数、隐式类型转换、`LIKE '%x'`、`OR` 两边有一边无索引、不满足最左前缀。

**Q16. 索引越多越好吗？**
不是。索引占空间，且每次 `INSERT`/`UPDATE` 都要维护所有索引，拖慢写入。一般一张表 5–6 个是上限。

**Q17. 事务的 ACID？**
原子性（全做或全不做）、一致性（合法状态到合法状态）、隔离性（并发互不干扰）、持久性（提交后不丢）。

**Q18. MySQL 的默认隔离级别？为什么？**
`REPEATABLE READ`。原因：MVCC 让 RR 代价很小；老版本 `STATEMENT` 格式的 binlog 在 RC 下会导致主从不一致；历史惯性。**注意 Oracle/PG 默认是 `READ COMMITTED`。**

**Q19. 脏读、不可重复读、幻读的区别？**
脏读读到未提交数据；不可重复读是同一行在同一事务内两次读不一样；幻读是同一范围的行数变了。前两个针对"行"，第三个针对"行数"。

**Q20. MVCC 是什么？**
多版本并发控制。每行保留多个版本，事务读自己开始时有效的那个版本，**读不加锁、写不阻塞读**。这就是 MySQL 用 RR 还不慢的原因。

**Q21. 持久性是怎么保证的？**
redo log（WAL）。`COMMIT` 返回前把修改写入 redo log 并 fsync，数据页可以之后慢慢刷盘。断电后重启重放日志恢复。

**Q22. 什么是长事务？有什么危害？**
开了很久没提交的事务。它一直持锁，会阻塞其他事务；还会让 undo log 无法清理。排查用 `information_schema.INNODB_TRX`。

### JDBC

**Q23. JDBC 是什么？**
Java 访问数据库的标准规范，由各数据库厂商提供驱动实现。

**Q24. JDBC 的步骤？**
加载驱动（4.0 后可省）→ 获取连接 → 创建语句 → 执行 → 处理结果 → 关闭资源。

**Q25. `Statement` 和 `PreparedStatement` 的区别？**
`PreparedStatement` 预编译、参数化，能防 SQL 注入，还能复用执行计划；`Statement` 是字符串拼接，有注入风险。

**Q26. `PreparedStatement` 为什么能防注入？**
它先把 SQL 模板发给数据库解析、固定结构，再把参数值单独发送。**值永远不会被当成语法解析。**

**Q27. `PreparedStatement` 能防所有注入吗？**
不能。表名、列名、`ORDER BY` 字段这些"标识符"位置不能用 `?`，必须自己做白名单校验。

**Q28. JDBC 怎么管理事务？**
`conn.setAutoCommit(false)` → 执行多条 SQL → 全部成功 `commit()`，任何异常 `rollback()`。
